# Conversation Pipeline settings

UI-20261030-01 / CHG-20261030-04 · 2026-10-30 · Ready for scoped implementation. Dependencies UI-20261029-01, REV-20261030-01 and SRC-109 DONE. User requests a Pipeline tab on Conversation and prioritizes required data/evidence before stage entry.

## Scope and compatibility

Settings → Objects → Conversation → Pipeline edits the existing tenant process. The catalog key remains `conversation_session`; the persistent `conversation` key is presented as Conversation Channel in this selector. No registry IDs, API paths, receipts or existing lifecycle semantics change. This is configuration for the current intake implementation, not acceptance of the future cross-channel need aggregate described in the [product model](../contracts/conversation-channel-model.md).

One current pipeline per tenant, immutable versions, up to 20 ordered stages and 1–12 behavioral milestones. Configure shows stage label, description, color, type, position and requirement summary; a per-stage editor selects required Conversation classification properties, an identified need, and milestone evidence. The second subtab is Tự động hóa with two system conversion-time rules. Existing milestone definitions are retained for guards/evidence. Processing close and Sales outcomes remain separate from stage entry.

## CHG-20261030-06 — System stages and conversion-time automation

Ready, user-authorized scope 2026-10-30, same task/dependencies. Typed definitions have four nondeletable system stage keys: `new` (Mới, Open), `received` (Tiếp nhận, Open), `converted` (Converted), `unqualified` (Unqualified). System keys and types are fixed; labels/colors/descriptions and permitted requirements remain editable. Mới is first and precedes Tiếp nhận. Custom stages choose Open, Converted or Unqualified in a Type column immediately after Màu. The last two types are closed outcome categories for this pipeline, without closing the messaging session or creating Sales outcomes.

Wire: optional stage `type` enum `open|converted|unqualified`; optional definition `automations` containing required booleans `set_convert_time` and `clear_convert_time`. Typed definitions require every stage type, all four system stages and new-first ordering. Legacy versions with neither addition remain readable/pinned and have no automation. Publication cannot downgrade a typed head to legacy or remove/change system keys/types. The editor upgrades legacy config in an explicit unpublished draft, preserving existing stage keys/requirements/milestones, adding missing system stages and defaulting custom types to Open. If more than 20 stages result, publication is blocked until custom stages are removed. A legacy `new` stage with requirements must have them explicitly cleared. New default process has Mới before Tiếp nhận, existing consulting/next_step stages, then Converted and Unqualified; both rules default on.

Rule 1: on a successful transition to a stage of type Converted, set Conversation `convert_time` to that transition's server UTC recorded time. Rule 2: on a successful transition to Open or Unqualified, clear `convert_time`. Each switch is independent; disabled rules preserve the prior value. A different Converted stage refreshes the timestamp; same-stage writes remain invalid. Failed guards/CAS, replays, needs/evidence writes and configuration publication do not change it. Rules use the session's immutable pinned version. No retroactive timestamps for legacy versions and no effect on milestone funnels.

Storage decision: derive `convert_time` from the latest applicable committed stage event under the pinned automation config. The immutable event is the durable effect, so no asynchronous worker or mutable duplicate timestamp is needed. Chat reads its own tenant/session ledger ordered by revision, independent of history pagination, and returns UTC timestamp or null in progress reads. Null also covers unenrolled and legacy sessions. Existing tenant/session/revision index supports the query; no DDL, backfill, new grants, cross-owner SQL or migration history edits. Permissions remain existing progress permissions. BFF/Chat contract binaries must be upgraded before publishing typed config; previous prepared images are now superseded and must be rebuilt before rollout.

## Exact additive contract

The existing session-process input/response and pinned progress definition gain optional stage `description` (max500), `color` (#RRGGBB), and `requirements` with optional `fields` (unique identifier keys, max100), `need` (boolean), `milestones` (unique configured milestone keys, max12). Omission preserves unrestricted historical behavior. The first stage cannot have entry requirements because intake must remain possible before collecting data. Duplicate/unknown milestone references and first-stage requirements reject publication. The editor selects field keys from existing Conversation classification properties. Entry checks stored values for the pinned keys; a missing key fails closed. This does not introduce metadata deletion or copy values from another object. Publication validates key syntax, not remote metadata existence; an admin submitting an unknown key through the API must correct it by publishing another version.

Every explicit stage move checks the target stage in the pinned version, under existing Conversation/session/progress locks, before writing any event/receipt/effect. Required classification values must be present, non-null and nonblank; false and zero are valid. `need` requires at least one session_need. Required milestones must have effective, non-retracted evidence for the same need in this session; replaced/retracted evidence does not qualify. A failed check returns `STAGE_REQUIREMENTS_NOT_MET` (422), without values. Existing reason, permissions, CSRF, CAS, idempotency and closed-session guards remain mandatory. Later data/evidence correction does not rewrite historical stage entry or move the stage automatically; a later entry rechecks current facts.

Chat obtains the target stage's required keys from its immutable pinned definition before admission and binds them in optional `session_read_fields`. Identity checks current `conversation_session` read field permissions for every required key. No custom value is fetched from another owner or disclosed by the rejection. Existing metadata catalog selects the keys; this introduces no cross-owner SQL. Old commands omit the field. Roll out accepting Identity/BFF/Chat binaries before using new requirements; an old binary must not handle enriched definitions or stage writes. Prefer forward fix; no binary rollback while guarded sessions are writable.

No transcript/PII is added to configuration. Test fixtures retain existing tenants and rows.
