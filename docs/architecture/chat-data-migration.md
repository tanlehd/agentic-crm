## Registry partition and reference integrity

The migration operator builds immutable set C from source SQL at the fenced snapshot:

```sql
SELECT c.tenant_id,c.record_id,r.object_type_id,r.version,r.owner_revision
FROM conversation c
JOIN crm_record r ON r.tenant_id=c.tenant_id AND r.id=c.record_id
JOIN object_type o ON o.tenant_id=r.tenant_id AND o.id=r.object_type_id
WHERE o.`key`='conversation' AND o.kind='standard';
```

No archived_at/status filter. Require both directions: every Conversation has exactly one correctly typed registry row, and every registry row whose object key is conversation has exactly one Conversation. Reject any Contact/Company/Activity/Lead/Deal/custom_record subtype with the same (tenant,id), including archived rows. Reject orphan/foreign-tenant children, duplicate active identities/episodes and ambiguous metadata. Tenant is a registered business tenant, including suspended historical tenants; suspension forbids runtime admission, not preserving history.

Copy crm_record where (tenant_id,id)∈C; ownership_history, record_team_access and property_index_value where (tenant_id,record_id)∈C. Keep actual IDs, owner/team/nulls, versions, custom values, indexes and history. Validate each property definition is for the correct Core object/type/version and each indexed value matches the retained custom value. Archived definitions/owners remain historical references; activation of a new use requires a current reservation/admission. Registry entry in Core becomes a read-only navigation projection after cutover; generic mutation routes by owner and never edits retained Chat rows.

The75 per-constraint entries in manifest preserve actual column order, referenced columns and update/delete rules. For36 local constraints, run child→parent anti-join using the exact composite columns and selected row sets; zero unresolved rows required, then install local FK. For19 outgoing constraints, preserve reference values and replace physical checks with Identity admit/directory, Core Contact/mapping/metadata reserve, Connector binding reserve and Chatflow proof. The ID-only outbound account FK becomes a logical native Identity account reference; never create a cross-tenant business FK to system account. Historical inactive identities are verified as historical, not silently reassigned.

For13 incoming constraints (Activity related record, associations, AI, Chatflow, Connector deliveries/touchpoint/receipt, Sales Lead and Routing attention), detach the complete physical constraint in baseline forward044 only after its replacement adapter and logical checker are deployed. Mixed rows continue to be validated by their actual owner. Do not detach subtype constraints: the six Contact/Company/Activity/Lead/Deal/custom_record→registry constraints stay in baseline, and their subtype rows must be disjoint from C. The one shared inbox→outbox FK is removed in baseline044 and omitted in Chat. Other169−75 constraints remain untouched. Retained source copies are historical evidence, not FK targets for new remote data.

Logical references without an existing FK also require validation: message reply target same Conversation, acquisition/message membership same episode, milestone message/need/correction parent, need_follow_up source/recovery episode and pinned run, D2 claim/job intent+attempt+grant+message binding, session contribution Sales outcome/source revision, session touchpoint Connector binding and all actor/owner/team/share references. Remote validation uses bounded owner proof APIs after adapters exist; T03 uses the fenced source metadata/rows as operator evidence and reports runtime API verification NOT_RUN until T06/T08. Failure/unknown is NO_GO, not a deleted reference.

## Four reliability ledgers: explicit row rules

Executable predicates live in scripts/lib/chat-data-partition.mjs and are materialized in manifest-v1.json. They consume validated tenant/entity indexes from the same snapshot. Strings compare byte-exactly, anchored full route/type/version matches only. They do not query a running service or authorize a user. Rules produce copy(Chat), retain-owner, explicitly authorized archive, or NO_GO. Complete row coverage and disjointness are required for the cutover manifest; a rule failure cannot be turned into a skipped row.

**idempotency_record:** apply the ordered, anchored receiptRules and same-tenant Conversation/session/need/catalog membership checks. Keep id, actor_kind/id, route_key, key, request_hash, response, status and expires_at verbatim. `/api/v1/threads/.../assessment|enrich` stays legacy even though the public adapter accepts Conversations. `need-outcome:<conversation>:<session>:<need>` stays Sales, including expired and pending receipts. Generic `/records/:id/assignment` resolves the actual validated record owner; Core metadata routes do not become Chat-owned merely because they mention conversation. Catalog route verbs are source `create/update/archive/shares`, including trailing slash for create; snooze route verb is source `snooze/wake`. No broad `/chat*` match.

Known non-Chat routes are retained by their explicit owner. For other historical receipts, the operator must produce a reviewed per-row classification containing table+tenant+PK+canonical row hash, source command site/hash, exact effect/owner proof and decision. This is an explicit compatibility exception input, versioned with the migration manifest and validated against that row hash; it is not a mutable default-owner callback. Unknown executable rows, including expired HTTP receipts, block migration until classified. Pending receipts must reach proven terminal state under the old authority before snapshot; corruption or an orphan pending row is NO_GO. No age-based discard.

Completed note receipt remains the Chat public parent. Its response_body.data.id must reference one same-tenant Core Activity note with related_record_id=Conversation, and the original source receipt hash must match. Import Chat command_id=receipt.id as a terminal legacy command, and import a Core terminal note child using deterministic UUIDv5(namespace=parent command UUID, name='note:v1'), child_key=`parent-command:note:v1`. Do not execute note-create during migration. Existing Activity body stays in Core. Legacy terminal import digest is SHA256 of canonical `{migration_format:1,tenant_id,receipt_id,request_hash,response_status,response_body}`; it is tagged legacy, never accepted as a prepared native admission. Original legacy hash remains separate; result replay requires fresh authorization. Missing/ambiguous child blocks. A previously expired-and-deleted receipt cannot be reconstructed from correlation alone; preserve domain dedup/history without inventing a parent.

**audit_entry:** exact Chat resource/action pairs in chatAudits select Chat audit, including denied audits with a nonexistent/null resource_id where the action/resource unambiguously identifies Chat. Accepted rows require same-tenant source membership. `sales_need_outcome/need.link_outcome` remains Sales; Core Activity/note body audits remain Core. Unknown immutable history can be retained only in the existing read-only baseline audit archive with explicit per-row authorization: owner, row hash, policy `legacy-audit-no-purge-v1`, approver identity and manifest digest. This T02 design does not grant that approval. Archive reader is a separate operator/Operations route under current tenant audit-read rights, with field/body redaction; ordinary Chat endpoints never fall back to SQL on baseline. No replay from audit archive, no retention timer/purge in local D3. Do not infer owner from correlation_id.

**outbox_event:** chatEvents requires exact event_type+schema_version+aggregate_type and validated aggregate membership; validate every strict legacy envelope/payload against its T01 referenced schema before classification. Acquisition/session/need payload IDs must match the same-tenant graph, including v1 thread_id and v2 conversation_id. Mixed record.assigned requires aggregate_type=crm_record, payload.record_id=aggregate_id and payload.object_type matching the validated subtype. contact.created stays Core. Core note and Workflow automation events stay at their producer even when consumed by Chat. Original id/version/correlation/causation/body/timestamps remain unchanged. Dispatched and failed events remain executable for replay and cannot use the audit archive escape hatch. Any unregistered event/version blocks until a versioned rule or exact source-backed retained-owner exception is approved.

**consumer_inbox:** classify by exact handler registration, not outbox producer. The eight Chat names and nine producer bindings in chatConsumers are complete for current Chat. Join original event only in the migration operator snapshot, verify producer/type/version/tenant, then copy the legacy dedup receipt and create chat_event_inbox with authenticated producer metadata/envelope/digest. Core/Workflow source outbox remains remote. Other existing handlers retain their owner and are listed in the T01 subscription matrix: Identity access, Routing access+four Human Routing handlers, AI access, four Workflow handlers. Match their exact event/version/producer allowlist before retaining them. Unknown handler/event is NO_GO. A legacy completed inbox becomes applied with the original processed_at; missing inbox for a registered delivery becomes pending. A source processing inbox requires old-handler reconciliation before snapshot. No FK to a remote producer, no remote event copied into Chat outbox.

## Initialization and state invariants

T09 / CHG-20261027-02 implements this bootstrap in `scripts/lib/chat-main-owner-plan.mjs` and `chat-main-owner-import.mjs`. Seeds are derived from the authenticated source43 snapshot after the Chat copy reconciles. The operator inserts and rereads exact owner rows in a transaction; replay inserts nothing and any changed gate/head blocks without overwrite. The main entrypoint additionally checks the final writer fence and preserves all original source rows across baseline44–46. Native rehearsal retains a separate schema and tests drift, cross-schema denial and allocation mismatch. Runtime grants/enrollment are a later explicit step; bootstrap never activates traffic.

Pre-prepare abort contains only command_id+binding_digest in T01. Thus owner_command allows null binding columns **only in an aborted tombstone**; prepared and committed native commands require the complete strict binding. No placeholder actor/resource is invented. Delayed prepare cannot fill or revive that tombstone. Legacy committed import uses known actor/resource and the tagged digest above; it cannot call apply/admit again. All child prerequisite slots are fixed from the operation; binding_digest cannot change on dependency settlement. Lock parent before child, and never terminal-abort a parent until every external child is proven aborted or the committed effect is reconciled.

All new mutable rows explicitly insert version=1, created_at/updated_at at the migration or transaction UTC instant. No implicit tenant or version values. Empty command/dependency/selection tables are correct except verified legacy terminal imports. Remote owners import their own terminal children/receipts with the same operator mapping. Identity admission table starts empty only after all old non-send transactions drained; native D2 delegation/grant ledgers stay at Identity. Business owner_gate/capacity_gate rows start open; account_gate rows are system-scoped for each native account. An absent gate is initialized under native account/tenant serialization before use, never interpreted as permission.

Gate seed barrier IDs are deterministic UUIDv5(namespace=run_id,name=owner+tenant+resource); request/binding digests are tagged migration seed evidence, never fabricated live command proofs. Nonarchived Contact guard and open tenant/account gates use these seed identities until the first actual operation. Identity owner_barrier/account_barrier preserve every real closing/completed operation separately from the current gate, so a later revoke cannot erase an earlier retry/status result. Account reset records contain only sanitized intent/security revision references, never a password/token. Admission locks account_gate and native account/session security rows, then tenant owner_gate/policy and principal rows; closing/drain follows the same order, and all code paths changing rights join that serialization before returning completed. Multi-account/tenant scopes sort IDs, with no SQL held during terminal-proof RPC.

Core/Connector reference_gate starts at actual owner revision/open or retired according to canonical state; no reservations are invented. Contact guard is archived for already archived Core Contacts, released for nonarchived Contacts; any active (status<>closed) Conversation for an archived Contact is NO_GO, including archived registry rows. A new guard closes before pending uses are enumerated and serialized with every prepare/reopen/ingress. Sales outcome_gate derives outcome_revision from canonical outcome rows; recovery reservations start empty only after old recovery is drained. Routing allocation_head is imported from existing active/terminal work/allocation and exact current Chat owner_revision, including unmanaged mode; mismatch blocks. Pending capacity reserves count with allocations under the same principal/tenant lock, no automatic expiry. Config gate blocks new reserves while draining old ones.

Chat control_head baseline: registry_revision=1, control_revision=1, pause/cancel=0 for each preserved Conversation; this initializes new counters, not record_version/owner_revision. Before consumer activation, inventory every retained active AI/Chatflow run/node. A run proved current by same thread/episode/owner fences is pinned generation1 in its owning store; old/ambiguous work is paused/cancelled under its existing lifecycle and reconciled. If a run cannot be proved current or safely terminal, NO_GO. No running generation can be guessed. New control events initialize every subscriber; subsequent control changes increment record_version and control_revision, with pause/cancel strictly below new control_revision.

Core/AI/Chatflow chat_projection starts from the validated minimized Chat snapshot and is updated only by authenticated cumulative events. It supplies navigation/cleanup freshness, never ACL. Core's retained crm_record Chat partition stays historical; generic navigation uses this explicit projection or fresh Chat API. AI/Chatflow chat_work_binding pins each existing run/node/execution attempt to the proved generation and original graph/version; explicit resume creates a new attempt key, never rewrites the old pin. Local projection lock serializes dequeue/lease acquisition with cancel/pause application. Equal registry revision with different digest quarantines; missing projection pauses work until authoritative snapshot arrives.

Five dataset heads (conversion/stage/progress/routing/registry) start revision1 per tenant. Every relevant fact, classification/process, owner/team/share/archive, message/reply, acquisition, need, evidence or contribution write increments affected heads in the same local commit. Snapshot prepare stores full bounded candidate once with page hashes; snapshot_validate checks head equality, not timestamps. snapshot/page start empty, never copy transient source reads. Five-minute reclamation aborts/settles admissions before deleting facts. Read/page admission still checks current rights. No JSON dump of arbitrary tables in snapshot facts.

Event stream identity is **producer+tenant+aggregate_type+aggregate_id+consumer**, as T01 requires. Allocate sequence under local stream lock in the producing transaction; delivery row stores immutable registration_digest and legacy event digest. Import events in deterministic (occurred_at,id) order within each stream, contiguous sequence starting1; this is a transport sequence, not a claim about old commit order. Preserve per-handler completed receipts. acked_through is the largest contiguous applied prefix, never MAX(sequence) across gaps. For historical Workflow trigger history, verify pinned enrollment/existing run IDs before ACK; replay absent receipts once without reselecting published graph. Receiver contiguous watermark is derived from its retained unique aggregate/sequence index and applied inbox prefix; no purge means no missing floor. A separate durable offset table is unnecessary in this local profile. Ten failures quarantine, do not advance ACK; replay uses the same IDs/digests.

## Grants, data representation and retention

Use exact table privileges in grants-v1.sql. Provision role membership separately, minimum host binding and separate secrets per API/worker/migrator. No GRANT OPTION, SUPER, FILE, PROCESS, cross-schema SELECT, runtime CREATE/ALTER/DROP or schema auto-sync. API/worker SELECT on journal/writer gate only; migration run/chunk are operator-only for writes. Audit/history/terminal immutable ledgers receive SELECT/INSERT only. Explicit deletes are limited to existing link/index/receipt replacement and settled report pages. Mutable command tables need UPDATE for state but immutable binding/terminal fields are enforced by CAS repositories, not claimed to be protected by MySQL row policy. MySQL cannot enforce business tenant row authorization through these grants: CD-07 tenant-negative repository tests are required.

Provisioner creates schema/roles and assigns them; migrator gets own-schema CREATE/ALTER/INDEX/REFERENCES plus listed DML, no source write grant. Source-export role is separately provisioned SELECT on the127 allowlisted source tables (including metadata/reference tables and journal), no runtime access, no DDL or DML. DDL on source for future043/044 belongs to a separate deployment migrator, never export credentials. Audit archive account is read-only on source audit and approved lookup metadata and unavailable to Chat runtime. Role mapping for co-located owners is table-explicit, never agentic_crm.* to every owner. Runtime source query/import is a cutover failure.

System tenant is the existing registered deployment ID01900000-0000-7000-8000-000000000001, supplied explicitly by provisioning and verified with Identity kind=system. Chat journal and Identity account_gate/account_barrier are system scope; all other new rows business scope. No wildcard/default tenant, no system fallback on missing context. Any deployment with a different registered ID must regenerate/review the exact CHECK artifact before migration; no runtime string substitution.

InnoDB/MySQL8.4, strict SQL mode, UTC connection time_zone, utf8mb4_0900_as_cs text and ASCII binary identifiers preserve case and sort semantics. Preserve microsecond DATETIME as strings through export/import; never JavaScript Date millisecond conversion. DECIMAL(20,6), uint64 and versions travel as exact decimal strings/BigInt, never Number/float. DATE remains YYYY-MM-DD, NULL distinct from empty/zero. VARBINARY encodes hex with type tag. Legacy JSON schema/bounds are unchanged; new protocol JSON must validate the exact operation definition and max256KiB before persistence. Typed identity/fence columns are queryable, JSON carries bounded versioned payload/proof, not independent relational authority. JSON key order is normalized for hashing only; arrays and values remain unchanged, no mass alias rewrite. Duplicate JSON keys rejected on wire; source JSON already has MySQL canonical semantics.

Canonical row hash v1: SHA256 UTF-8 JSON array in physical column order of `{name,type,value}`; NULL explicit, integer/decimal/date/time/binary typed strings, JSON recursively codepoint-sorted object keys (arrays preserved), no Unicode normalization. Include generated columns in comparison, omit them from INSERT. Hash each PK-ordered row to64lowercase ASCII hex characters. Chunk SHA256 input concatenates, for each row, unsigned32-bit big-endian length64 followed by those64ASCII bytes. Table hash input is canonical JSON of the ordered array of {chunk_number,row_count,chunk_hash}, with numbers represented as unsigned decimal strings. Tenant hash input is canonical JSON of table-name-sorted {table,row_count,table_hash}; preserve the declared chunk size1000 except the final chunk. Compare exact bytes and source/target values independently; counts alone are insufficient. Hashes of actual content remain in private operator artifacts, never public logs or tracker.

JSON numeric tokens must be decoded losslessly (arbitrary precision/token-preserving parser), normalized as decimal numeric values without binary floating-point conversion; ordinary JSON.parse on raw source JSON is not an acceptable row-hash implementation for large numbers. The metadata generator uses JSON.parse only on schema metadata, never exported business values. CD-05 includes JSON integers beyond2^53 and decimal tokens so a lossy copier cannot pass by comparing its own rounded values.

No local automatic purge of messages, notes, audit, command/dependency/admission/reservation tombstones, events/inboxes, snapshots of migration or old source. Temporary report page cleanup and existing seven-day public receipt response expiry are exceptions; permanent domain dedup and terminal command ID remain. Purging encrypted source export/backup requires a later explicit retention decision after T09 rollback/restore proof. Encrypted backups capture each owning schema, journal checksums, writer epochs, admission/gate state, pending child/delivery envelopes and contiguous watermarks. Keep encryption keys outside DB/logs and backed up under operator control. A restore is fenced until all owners reconcile admissions, downstream effects, provider attempts and inbox/outbox gaps. Local target RPO=0 to last committed fenced export; RTO must be measured in T03/T09, not asserted here. Production retention/RPO/RTO remains a deployment gate outside local D3.
