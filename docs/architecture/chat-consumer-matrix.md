## First transaction to replace: assignment/takeover

Current entry `Routing.mutate` holds tenant authorization lock, reads registry, opens durable receipt, checks capacity/Identity eligibility, updates registry and history, invokes Chat assignment hooks, cancels AI/Chatflow, synchronizes Routing work and completes the receipt in one database transaction. The source call chain is `agents/routing.ts → crm/registry.ts → conversation/ownership-port.ts`. Moving `RecordRegistry` alone would leave remote writes in that transaction.

The Chat-local commit must include all of the following under one locked Conversation record and expected-version check:

1. Validate tenant/resource binding, active thread, actor permission, expected version and target owner/team eligibility proof. Team clearing retains the current configure-capability rule; takeover target is the authenticated principal.
2. Increase record version and owner_revision exactly once, including the current same-owner assignment behavior. Retain custom values, archive state and object-type ID; do not reset version to 1.
3. Append history, assignment activity and session contribution using the old and new owner/team snapshot; wake snooze; cancel only queued/remote_queued intents and their messages. Already sending/unknown states retain their reconciliation path.
4. Commit command receipt, audit and versioned owner/control notifications atomically. The response is authoritative for local owner change, not confirmation that remote runs have stopped.

Remote preparation occurs outside this SQL transaction. Capacity reservation must have a stable operation ID and a status lookup; a lost Chat ACK is resolved by Chat receipt before release. AI/Chatflow reconcile their runs after Chat fences new dispatch. Core generic navigation follows Chat record authority; it cannot continue mutating its retained copy.

**Open design decisions to specify, not user approvals:** exact Identity admission/consume protocol for non-send operations, target eligibility and Routing reservation binding; typed command/result/proof schema; durable pending-command state and failure recovery. Existing D2 send grants are bound to intent/message/attempt and cannot be relabeled as general-purpose assignment permission. A remote `allowed=true` followed by a later SQL commit does not reproduce the old tenant-lock revocation guarantee. Do not implement a TTL permission cache to hide this gap.

## Legacy reliability partition findings

Partition by actual command/producer/consumer authority, never by source folder or event prefix alone:

- `need-outcome:<thread>:<session>:<need>` is handled in Chat source today but mutates Sales outcome data. Its receipt/audit cannot be classified as Chat simply because of the file path.
- Note creation has a Chat public receipt and a Core Activity effect; preserve both old receipt identity and new owner reconciliation. Generic CRM assignment receipts embed only a resource UUID and require the validated Conversation set.
- Need assessment deliberately uses legacy `/api/v1/threads/...` receipt keys despite canonical public `/conversations/...` routes. Do not rewrite keys during extraction.
- `record.assigned` is emitted for multiple resource owners; match object type and same-tenant aggregate ID. `contact.created` remains Core even when caused by ingress.
- Chat has eight concrete current consumer names: `chat.read-marker.v1`, `chat.snooze.v1`, `chat.inbox.changed.v1`, `chat.snippet.changed.v1`, `chat.tag_definition.changed.v1`, `chat.conversation-tag.v1`, `chat.activity.note.v1`, `chat.activity.automation.v1`. The last two consume remote Core/Workflow events; their source outbox rows do not belong to Chat.
- Baseline `consumer_inbox` references `outbox_event` physically. Target inbox needs an authenticated remote event reference instead, while preserving dedup status. Copying every source outbox to satisfy the FK creates the wrong authority.
- Denied audits may have no resource ID. Keep unresolved history in a read-only legacy archive with explicit owner routing until a reviewed rule classifies it; never silently drop or wildcard-copy it. Cutover cannot proceed with unresolved executable receipts/events.
- Capability guards currently test baseline migration numbers 20/21/22. New Chat journal versions must describe Chat migrations; replace guards with explicit supported capabilities, never fabricate baseline journal rows.

## Cutover order and rollback requirements

Complete exact contracts/table templates first. Then provision retained destination separately, copy a fenced snapshot with exact tenant/ID/version/hash comparison, and validate both directions of logical references. Exclude runtime dual-write. During final switch, stop every mapped old writer/consumer, drain or reconcile its durable operations and reject new old-owner commands before enabling Chat. Baseline Core/Sales subtype FKs remain valid for their own registry partitions; they must not be dropped merely because the registry table name is shared today.

Before any destination write, rollback can restore old routing after verifying no destination effect. After destination writes, old rows are stale: freeze the new writer, reconcile/replay a verified reverse delta or use forward recovery. A routing toggle is insufficient. Existing D2 image/container activation is not evidence of either physical cutover or reverse replay.
