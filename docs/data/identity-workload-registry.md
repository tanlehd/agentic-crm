## Admission and operator contract

Only three service identities: identity, chat, connector. Each has one registry row, operator-controlled enabled flag and monotonic version. Certificate identity is SHA256 of the exact leaf DER; SAN must ultimately be exactly `URI:spiffe://agentic-crm/service/<service>` with operator CA verification in the TLS adapter. Register accepts trusted operator metadata (fingerprint, not-before/not-after epoch milliseconds); it does not prove a certificate chain. Leaf lifetime >0 and <=24h. Register/rotate requires currently valid leaf. No runtime API may expose these operator methods.

Rotate locks the service row, validates expected version, rejects an already registered fingerprint forever, shortens every older nonrevoked certificate's admission deadline to min(existing deadline, SQL now + overlap), inserts the new certificate and atomic audit. Overlap is explicit 0…3600000ms. The service lock serializes concurrent rotations/revokes; old deadlines never extend. Disable/re-enable and tenant scope changes require expected service version and increment it. Revoke is terminal; enabling service does not reactivate a revoked/expired certificate. Lost ACK is reconciled by reading version/state, never blind mutation retry.

Authorization reads one current SQL statement joining service/certificate/business admission/tenant roots. Requires registered active system tenant, active business tenant, explicit enabled business scope, enabled service, exact fingerprint, not revoked, not_before <= SQL now < min(not_after,accept_until). Missing data denies; database failure is DEPENDENCY_UNAVAILABLE. No TTL cache; every request including keepalive must call this port. The query snapshot is admission's in-flight boundary; later revocation cannot recall an already admitted request. This decision is not a portable capability or a replacement for current Human authorization. Chat/Connector cannot query these tables; future authenticated Identity API owns remote checks. Peer strings or body fingerprints alone are never TLS evidence.

## Filled table templates

Shared review for all four tables: [template](../templates/database-table.md), [catalog](schema-catalog.md), [guideline](database-guidelines.md). Requirement REQ-01/02/07; acceptance WLR-01…07 below. Physical baseline database only in retained `native_identity_test` for acceptance; target `crm_identity`. Identity is sole writer. No cross-service SQL/FK. Every table has tenant_id CHAR36 ASCII binary NOT NULL, no default. System scope is registered PLATFORM_TENANT_ID; business scope explicitly excludes it. No keys, PEM, tokens, sessions, transcripts or provider credentials stored.
