## Transport and ownership

All five POST routes live under `/internal/v1/chat-exchange/`: `payload-put` (Chat → Connector), `ingress-accept`, `ingress-read` and `cancellation-read` (Connector → Chat), `connector-cancel` (Chat → Connector). Use dispatch v1 TLS1.3/mTLS/active workload registry profile and business tenant admission. No actor identity from headers or body, cookie, query, redirect, supplied URL or provider secret. Only authenticated configured owners can invoke these operations; opaque IDs alone authorize nothing. Reads/replays recheck current workload/tenant/resource access before returning a receipt. Control and receipt bodies cap16KiB; payload-put/ingress-accept cap96KiB raw UTF-8 JSON, with normalized content/intake independently capped64KiB. Responses are no-store. RPC timeout2s except ingress-accept/ingress-read, whose composed current-authority/reservation/commit/settlement deadline is10s (CHG-20261025-03). Each nested owner RPC retains its own bound. No transcript in errors/audit/logs. HTTP parser must reject duplicate JSON keys before validation; this parsed-object kit does not implement a parser or mTLS.

Compatibility: shared transport applies the same exact-path deadline on client/server. Request/reply shapes, deduplication and current admission are unchanged. A prior2s caller can still time out and retry the exact request or query its receipt; a timeout never proves absence or authorizes another effect. No DDL or downstream business rollout is required.

Version1, UUID request_id and strict DTO per operation. Request ledger key `(target,tenant,caller,operation,request_id)` binds the entire validated request digest. Same key/different body409. Lost ACK retries use the identical body/key; new request IDs still deduplicate on the resource/event/attempt keys below. Nonmutating reads return current state, never a cached admission. Consumers validate operation-specific reply schema, authenticated owner, request_id and expected receipt/resource IDs from their bound request context; a schema-valid reply alone proves no authority. No TTL purge of request/event/message/cancellation tombstones in this slice; retain through intent/delivery lifetime plus restore/replay horizon. Payload retention and production purge need separate policy/evidence.

Error body `{request_id,code}` only: INVALID_REQUEST400, UNAUTHENTICATED401, FORBIDDEN403, NOT_FOUND404, CONFLICT409, REVOKED403, EXPIRED409, INVALID_TRANSITION409, DEPENDENCY_UNAVAILABLE503. Dependency errors are retriable with unchanged keys and never interpreted as absent mapping or permission. No automatic retry of an outbound provider effect.

## Payload binding and dispatch order

`payload-put` contains exact DispatchBinding, grant_id and payload `{version:1,platform:"mock_messenger",message:{type:"text",text}}`. Text1–4000 nonblank characters; rich outbound remains excluded because current Sender accepts text only. No relabel of mock as real Meta, media URL resolution, trimming or Unicode normalization. SHA256 over UTF-8 recursively key-sorted JSON of this exact payload must equal binding.payload_digest. Array order and literal Unicode remain significant, whitespace outside strings/property order do not. JSON serialization follows the existing JS canonical implementation; no numbers beyond version1 occur in this payload.

Connector stages an immutable payload per tenant+intent/attempt only after authenticated Chat intent binding, active connection and current Identity delegation/policy checks, exact issued grant inspection and TTL. Grant/binding/resource snapshot must agree. These remote checks are explicit ports, never direct SQL or authority inferred from JSON Schema. Payload transfer is not permission to send. Prepare requires matching staged content; Chat claim then Identity consume and local Connector start remain required. Payload substitution or second attempt for the same intent conflicts. Same payload replay rechecks current read/staging rights, cannot refresh grant TTL and never rearms an attempt. Already consumed grants allow only the identical existing stage acknowledgement while current policy/resource/TTL still pass, never new staging. Expired/revoked grants deny staging even for duplicate requests; cleanup/status use separate owner authority.

Plain text additionally obeys the existing backend limit of4000 JavaScript UTF-16 code units (including inbound text); JSON Schema maxLength counts Unicode code points, so the semantic validator must enforce this stricter compatibility limit. This is not a license to truncate or normalize text. Existing rich-content worker preview validation remains part of lifecycle adapter parity.

Order: issue → payload-put → prepare → claim → begin (consume/start internally). Existing seven dispatch DTOs remain unchanged. Immediately before the first provider invocation the Connector rechecks stored payload digest and exact binding; corruption fails closed, no effect. Persisted payload and old prepared/consumed receipts cannot restore volatile invocation permission after crash. Historical payload-put receipt is `{state:"staged",receipt_id:attempt_id}` only, no content; it does not mean the attempt remains dispatchable. New protocol paths are not callable on current deployments.

## Inbound compatibility

`ingress-accept` carries source_delivery_id (stable Connector delivery UUID), `binding:{tenant_id,connection_id,crm_contact_id,crm_identity_id,mapping_revision:"1",platform:"mock_messenger"}` and **unchanged intake-request** from [contact-bound intake](contact-resolution-local.md). Generated schema embeds the canonical intake definition including normalized rich content, referral and text_source; no arbitrary provider payload. `occurred_at` canonicalizes to UTC millisecond form before event digest, rejecting impossible dates. Connector resolves mapping through CRM only on authoritative miss; Chat independently validates mapping against subject/tenant/connection/contact/identity and active Contact on accept and on processing, including cached hits. Mapping1 is immutable; remap/merge needs another contract. Outage is503, mismatch409, archived/revoked denied. Peer/binding/current read checks also apply to ingress-read and duplicate accepts.

Three distinct keys: request ledger; `(tenant,connection,source_delivery_id)`; `(tenant,connection,provider_event_id)`. A source delivery cannot be reused for another event/body. Same event and normalized binding+intake digest returns original Chat receipt even if source_delivery_id changes; altered event payload conflicts. Accepted status `received` means Chat's local inbox transaction committed, not message/Contact/automation completed. Receipt read contains no text or external subject, only receipt_id, state and, when processed, conversation_id/message_id/duplicate; failed contains sanitized error_code. It is tenant+connection scoped and verifies the receipt's stored Contact binding. Source delivery and event aliases are committed atomically with acceptance.

Processor validates authoritative mapping/Contact again, then commits message, source key, existing domain lifecycle effects, audit/outbox and processed receipt in one Chat-local transaction. Reference model exercises only inbox/message keys and injected lifecycle IDs; it does not simulate the full Inbox/routing/need/Reporting lifecycle. Dependency outage leaves received, eligible for retry; permanent invalid binding or message conflict becomes failed. New event with same provider_message_id must match identity/contact, occurred_at and exact normalized message; different text/content is MESSAGE_PAYLOAD_CONFLICT, matching current contact-bound v2 receive behavior. A duplicate never creates another message/session/touchpoint/trigger; extra referral/display label cannot rewrite original attribution. Same event with altered referral still conflicts at event digest.

`conversation_id` remains the long-lived canonical thread ID; `session_id` remains the episode. Ingress does not accept either from Connector. Chat selects them using existing [session rules](customer-360-session.md), including late/unresolved messages and new-ad-within-open-session behavior. Minimal processed receipts deliberately omit session_id: they do not invent a session for late unresolved data. Current legacy text/envelope2/envelope3 APIs stay unchanged.

## Cancellation and receipt replay

Owner takeover/close first atomically cancels queued Chat intents plus its own cancellation receipt/outbox. This local CAS competes with Chat claim. Before claim it wins; after claim it returns in_flight (or current sent/unknown), never claims recall. A committed Chat cancellation_id binds the entire original DispatchBinding and reason `owner_changed|conversation_closed|authorization_revoked`. The new `connector-cancel` carries that binding, cancellation_id and reason. Connector verifies this receipt with `cancellation-read` (exact binding + cancellation_id) at Chat before committing a cancelled tombstone; notification failure must not undo local cancellation. The read returns cancelled/cancellation_id/reason, with receipt_id=intent_id; unknown proof404. Both operations return the same minimized proof shape with request correlation. Notification and read use current workload cleanup authority, not the revoked sender's delegation.

Cancel is accepted before payload/prepare and blocks later reordered staging/prepare/begin. Prepared may become cancelled; admitting/started/sent/unknown cannot be relabeled cancelled. Duplicate cancellation returns its immutable acknowledgement with current owner read rights; receipt replay never executes a provider. Binding disabled or original sender revoked must not prevent cleanup by authorized Chat workload, but inactive tenant/workload still denies remote requests. A forged/mismatched proof or foreign tenant fails closed. No dependency on cancelling AI/Chatflow remotely before protecting Chat; their separate protocol remains a later gate.

Ingress received→processed/failed, cancellation acknowledgement, and dispatch unknown→sent are different receipt families. An old received ACK remains historical after processing; ingress-read is current truth. Old prepared/started/consumed ACKs never start again. Dispatch result rules remain unchanged: matching late sent evidence may resolve unknown; timeout, missing/negative lookup or failed replay cannot reset unknown. No automatic retry/rearm of the same outbound intent, and no retry policy change to the existing monolith.

## Compatibility, data and acceptance

No changes to existing intake, message content, dispatch schema or applied migrations. New schema/types/OpenAPI are additive. New worker activation is disabled until backend/worker/Connector contracts and own ledgers exist together; drain/reconcile legacy queued and lost-ACK deliveries before switching namespaces (as in [bridge upgrade](connector-bridge.md)). Never replay old legacy-body hashes as new exchange bodies. No dual writer, schema auto-sync or reset. Logical staging/transport records belong to Connector; inbox/source keys/cancel proof belong to Chat; mapping remains CRM; delegation remains Identity. PLAN-007B must provide table templates, tenant keys, grants, retention/backup/restore manifests before actual persistence implementation.
