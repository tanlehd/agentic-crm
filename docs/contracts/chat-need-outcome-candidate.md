# Chat Human need outcome link candidate

SRC-109/T05, CHG-20261023-07, C2, scoped Ready. Refines the existing [need outcome contract](need-follow-up.md), [assessment candidate](chat-need-candidate.md) and [owner protocol](chat-owner-v1.md). No new business behavior or AI provider activation. Native execution NOT_RUN.

Preserve POST /conversations/{conversation}/sessions/{session}/needs/{need}/outcome and deprecated threads alias, authenticated Human session/CSRF, If-Match and Idempotency-Key. Conversation read/update, text read/write, contact_id read and active Contact remain mandatory. Sales requires current Lead/Deal read and Lead qualify or Deal update, contact_id read, same Contact and exact Conversation/session context. Closed sessions remain supported. Linking creates neither a Lead nor a new assessment revision.

Every call, including imported receipt replay, uses a fresh Chat delivery guard and validates the current assessment version. Sales inspects its own registry/shares/contact/context under that guard and asks Identity for a finite decision on that exact resource. The result contains the authorized OwnerResource and a digest of its local source snapshot, never a Sales body or raw Access. Chat pins the target record, assessment version and immutable Sales snapshot in a separate effect command keyed by tenant/principal/legacy route/key. Legacy route is need-outcome:{conversation}:{session}:{need}; request hash is the unchanged original body/version hash. Different payloads under the same key conflict.

Identity admits the effect using pinned Conversation and Sales resources and canonical field-object IDs. Chat accepts one pending sales-outcome dependency while holding its local Conversation/command/need locks, rechecks the assessment version, and then releases SQL before remote I/O. Once accepted, assessment writers and follow-up recovery must refuse to advance that need until the child resolves. T06 must mount this same fence in external workflow recovery; a timeout cannot mean no outcome. Pending links do not prevent read-only assessment inspection. Competing link commands may coexist at the same assessment version; each retains its own permanent receipt.

Sales validates the pending parent and current Identity admission, rechecks its full pinned source snapshot under local locks, and atomically INSERT IGNOREs the exact sales_need_outcome plus a terminal sales_owner_command receipt. The existing natural key (tenant_id,need_id,record_id) preserves link dedup across keys. The reviewed Sales receipt table stores only IDs/digests/finite resource snapshots and original correlation. No Chat or CRM table access, remote SQL/FK or shared transaction is allowed.

Sales link and abort serialize on the permanent receipt row. Abort before link installs a tombstone; a delayed request cannot recreate the effect. If link already committed, abort returns its immutable terminal receipt and Chat completes its own minimized audit/public receipt without deleting the Sales link. Reconciliation uses the accepted original assessment and session pins; it does not re-authorize a new effect. Fresh public delivery still requires current version and rights. An outcome committed before later assessment changes remains linked; the old request then returns VERSION_CONFLICT as baseline does.

Generic Chat abort cannot abandon a pending/committed Sales child. Identity account/policy drains dispatch this exact effect to the outcome resolver, which calls Sales abort/read and finishes or aborts Chat before the barrier completes. Sales outage leaves the barrier and need mutation fence pending. Recovery is repeatable after restart using stored command and dependency state. A terminal aborted effect remains terminal under its key; a new explicit action uses a new key.

Storage: reuse reviewed [sales_owner_command](../data/chat-extraction-tables.md#crm_salessales_owner_command), exact owner-additions-v1.sql checksum, in retained native_identity_test only for candidate verification. No change to historical migrations or broad detach script. Chat uses its existing owner command/dependency ledgers; no new Chat DDL. Source Sales tables stay Sales-owned in the baseline group until their own extraction. Main provisioning/cutover remains T09-gated.

Acceptance: current Conversation/Contact/Sales field and record rights on initial and replay calls; exact tenant/session/need/contact binding; stale assessment version even on replay; concurrent/lost-ACK retries; legacy response adaptation only at known top-level thread_id; source snapshot race; abort-before-link and link-before-abort; actual Sales outage; pending assessment fence; native logout/drain; durable one link, terminal receipts, no assessment version increment; closed session and public CSRF/ETag. Native Sales tests must use actual Lead/Deal rows, not only context registry fixtures.

Candidate runtime grants: t05_sales_outcome_test has SELECT on own registry/object metadata/shares/Lead/Deal/session context, SELECT+INSERT on sales_need_outcome, and SELECT+INSERT+UPDATE on sales_owner_command. Snapshot reads use shared locks; no extra Lead/Deal write privilege. Source ACL is checked before reporting Contact/session binding mismatch. The provisioning helper hashes both reviewed and installed DDL, compares existing link count, and does not detach any FK or reset fixtures.
