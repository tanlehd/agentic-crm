## Source findings and authority

Current conversation/domain.ts closes Chat state, queued sends, agent executions and Chatflow sessions in one shared transaction. agents/cancellation.ts releases capacity and cancels pending tools; chatflow/lifecycle.ts pauses on owner change and cancels on close, incrementing node fences. These remain active until actual extraction. CRM registry currently holds Conversation owner/version/team/shares. The target moves only Conversation registry partitions into Chat; CRM metadata remains canonical and a CRM navigation catalog is a projection, never authorization or mutation authority. No table is moved here.

The projected record contains tenant_id, conversation_id, crm_contact_id, crm_identity_id, connection_id, nullable owner_principal_id/owner_kind/team_id/active_session_id, shared_team_ids, status(open/pending/closed), archived, record_version, owner_revision and the three new control counters below. All references are opaque, no labels, transcript, message body, policy lists, secrets or account/session credentials. Unassigned owner requires both owner fields null. `conversation_id` remains the long-lived thread; `active_session_id` is the nullable episode, not Chatflow execution session ID. Historic versions and IDs are preserved on migration, not reset to1.

## Revision and cumulative cancellation

`registry_revision` is a dedicated positive decimal string, incremented for every snapshot-affecting owner/record/team/share/contact/session/lifecycle change. It is not inferred from legacy record_version: migrations must establish its baseline. `control_revision` is a separate positive decimal generation used by every admitted AI execution/Chatflow node attempt. Increments for owner transfer, close/archive and episode replacement/reopen; no timestamp or JavaScript Number comparison. Maximum20digits, overflow fails closed. Plain metadata changes may increment registry_revision alone.

Two cumulative nonnegative watermarks are persisted in the same Chat transaction: `pause_through_revision` and `cancel_through_revision`, both strictly less than current control_revision. Owner change raises pause_through to the old control generation; close/archive/episode replacement raises cancel_through to the old generation. Reopen advances generation but never lowers watermarks. Chat cancels its queued sends and emits the full minimized snapshot atomically with local owner/state/receipt/audit/outbox. Owner/record versions and all counters are nondecreasing; any changed snapshot requires a strictly higher registry_revision. No cross-service UoW/FK.

Consumer applies **cancel first**, then pause: a queued/running AI execution with admitted control_revision at or below either watermark is cancelled, loses its local tool lease/fence and releases capacity once. A running/waiting/paused Chatflow attempt at/below cancel is cancelled; at/below pause it becomes paused_human and its pending nodes lose leases. Variables/pinned graph version remain. Terminal completed/failed/cancelled work is not reopened or rewritten; paused work may later be cancelled. A later pause notification cannot hide an earlier close: every newer snapshot includes both cumulative maxima. Delayed old events cannot affect new-generation jobs, and restored consumers can cancel old jobs from the current snapshot without receiving all historical notifications.

Compatibility with dispatch v1: every control_revision change also strictly increases record_version, and every owner_revision change advances control_revision/pause watermark even when assigning back to the same principal. Existing DispatchBinding already pins record_version/owner_revision; Chat claim must compare those live, so a close/reopen cannot make an old queued binding valid again. No dispatch DTO change is required. In-flight claims retain their original admission semantics. Backfilled active runs must receive a pinned generation through migration reconciliation before consumer activation; never guess that an old run belongs to the current generation.

Registration and local dequeue must serialize against the consumer's watermark. New work cannot bypass it by arriving after a cancellation. Snapshot knowledge never authorizes an effect: each Chat mutation still checks live Identity authorization and Chat's current owner/control generation at its owning transaction; sending uses dispatch v1. Cached registry/control values are hints and cleanup fences only. A request already admitted at the owner retains its specified in-flight semantics; no provider recall or globally atomic revoke. Generic Sales/CRM tools and remote routing proposals require their own exact action contracts before activation, outside this first slice. Chatflow resume must explicitly bind a fresh admitted generation; replay of a pause event does not resume anything.

## Private read and reference operations

POST `/internal/v1/chat-control/{operation}`, schema_version1 and UUID request_id, JSON-only/no queries,16KiB raw request/response cap. TLS1.3 mutual TLS, verified SAN `spiffe://agentic-crm/service/{chat|crm|identity|connector|ai-runtime|chatflow}` and current per-request workload registry/business-tenant allowlist. CA/cert24h/rotation overlap1h/dependency failure profile follows dispatch v1. Service body/header IDs do not establish peer identity. No Human cookie/credential or delegated end-user impersonation on these narrow service-purpose ports. Native public/BFF/External API reads keep their current independent ACL/field rules.

| Operation | Caller → owner | Request beyond common version/request ID | Successful reply |
|---|---|---|---|
| registry-read | crm, ai-runtime, chatflow → chat | tenant_id,conversation_id,minimum_revision | request_id + complete RegistrySnapshot with revision at least minimum; never stale cached fallback |
| event-read | crm, ai-runtime, chatflow → chat | exact ControlNotice (below) | exact immutable ControlEvent matching notice key/revision; unknown404, missing retained source503/attention |
| contact-check | chat → crm | tenant_id,connection_id,crm_contact_id,crm_identity_id,external_subject_id,mapping_revision1 | status current + observed_revision of active Contact; exact immutable mapping and current active Contact required |
| connection-check | chat → connector | tenant_id,connection_id,platform mock_messenger | status current + observed_revision of active registered connection |
| principal-check | chat → identity | tenant_id,principal_id,kind human/ai,team_id nullable | status current + observed_revision; active principal/kind and active membership in requested team if nonnull; this is not a reply/assign permission grant |
| metadata-check | chat → crm | tenant_id,object_key conversation,schema_revision | status current + observed_revision matching requested published metadata head; schema knowledge does not grant field access |

Every read rechecks current caller/workload/tenant/resource-purpose access; references are positive checks only. Missing/foreign returns NOT_FOUND404; immutable mismatch/stale revision CONFLICT409; inactive REVOKED403; authority outage DEPENDENCY_UNAVAILABLE503. Unknown property/malformed/version INVALID_REQUEST400, bad peer UNAUTHENTICATED401, wrong caller FORBIDDEN403. Reply `{schema_version,request_id,code}` for errors; no body echo. Success no-store, no persisted permission grant. A check result is current at its owner's read boundary, not a lease across the next service commit; privileged operations must retain their explicit owner admission boundary. Same request ID on reads may yield newer observed state; consumers validate correlation, target, bound request and operation-specific reply shape before use.

Source contract kit models already authenticated authority ports; it cannot satisfy real reference/native policy/crypto tests. No schema change or change to current contact cache semantics. Confirmed immutable mapping cache may still be used, but active Contact and active connection cannot be inferred from cached status.

## Durable notification, recovery and quarantine

One event type `chat.registry.changed.v1`, producer chat, schema_version1: event_id,tenant_id,conversation_id,registry_revision,occurred_at,correlation_id,snapshot. Snapshot keys/versions must agree with envelope. Every snapshot contains cumulative control watermarks, including pure registry changes and archive tombstones. Payload max16KiB, no arbitrary data. Breaking changes require a new event type/version; existing record.assigned/message/acquisition events and pinned Workflow handlers are untouched.

Broker receives only `ControlNotice:{schema_version:1,event_id,tenant_id,conversation_id,registry_revision}`. Relay publishes from committed Chat outbox; subject `crm.chat.registry.v1.<tenant_uuid>`, message ID event_id, mark dispatched only after broker ACK. Retry keeps event ID. Consumer obtains canonical event via event-read from authenticated Chat, verifies notice equality and schema; broker body is never a write/authorization command. Publish ACL only Chat relay, subscribe only configured crm/ai-runtime/chatflow tenant scopes; operator admin separate. Test/local stream one replica; production target3replicas/quorum must be measured before promotion. JetStream proposed transport profile: file-backed limits retention7days, explicit ACK/30s AckWait, max pending1000 per consumer, backoff1/5/30/120/600seconds and10delivery attempts. This profile is specified, not installed. Kafka Workflow streams remain PLAN-024B.

Durable dedup key `(tenant,producer chat,consumer version,event_id)` stores canonical event digest. Same ID/different body is quarantined CONFLICT, no mutation. Consumer version IDs `crm.chat-registry.v1`, `ai-runtime.chat-control.v1`, `chatflow.chat-control.v1`; names must not change on restart. Incoming revision=current+1 applies snapshot/inbox/job cleanup in one local transaction; stale lower revision records ignored receipt; equal revision with differing snapshot is conflict. Gap persists pending notice/inbox with required revision, blocks projection use and new work registration, then requests registry-read with minimum_revision=max observed pending revision. Authoritative snapshot may skip gaps only if its counters/owner/record versions do not regress. Replay same request/event never duplicates cleanup or restarts jobs.

Broker ACK only after local applied/stale/pending/quarantine transaction commits. Crash before commit means redelivery; crash after commit/before ACK replays dedup. Pending is not completion: own recovery worker owns it after broker ACK. Unknown schema, malformed authoritative body, counter regression and conflict create sanitized quarantine+attention, never a successful business effect. No raw body/transcript in quarantine logs; store identifiers, digest, allowlisted reason in own protected ledger. Invalid/spoofed broker notice is rejected without owner effect; security telemetry retains sanitized identifiers only. If local DB fails, no ACK. If source reference/event read fails, no synthetic missing result or effect; retry same notice, after10failures persist attention before ACK. At1000pending entries backpressure/NAK; no unbounded in-memory queue.

On restart/backfill/restore, consumer starts not-ready for side effects until it loads its durable watermarks/inbox and reconciles pending gaps against the owner. Missing durable state cannot bootstrap to a stale event revision; initial snapshot required. Archive tombstones survive restore and replay; no hard deletion or automatic TTL purge. Source outbox/event lookup, consumer digest/control tombstones, snapshots and backups span intent/run lifetime plus replay/restore horizon, **not only broker7days**. Production retention/purge, RPO/RTO and real restore drill remain deployment gates. If retained event is unavailable, source current snapshot may repair state, but unknown historical event cannot be declared processed; attention remains for provenance reconciliation.
