CRM owns Activity registry, note body, ownership and ACL inputs. Chat owns the Conversation and parent command. GET /conversations/{id}/notes preserves ascending UUID pagination, default50/max100, archived-note exclusion, independent Activity read rights and optional body redaction. Viewer read entitlement remains valid. No Conversation registry copy or foreign SQL is needed to list notes: CRM filters its own Activity.related_record_id by the exact Conversation ID in the authenticated Chat parent proof.

CRM note-list receives that parent reference and admission, verifies the current prepared proof, and requests a finite Activity read policy from Identity using the same parent. CRM uses those predicates against its own current registry/shares, then selects only allowed fields. Chat rechecks its Conversation snapshot under the writer gate before committing delivery. A completed Identity barrier aborts the parent and prevents delivery. Owner outage fails the note collection; activity-stream hydration may separately expose partial freshness under its own contract.

The previously unmounted private note-list placeholder is refined to an admission-bound recovery request; public DTOs, IDs and UUID cursors stay unchanged. No physical schema or data migration is needed for reads. Note creation, durable child recovery and activity notification reconciliation remain separate acceptance within this same active T05 task. Creation requires Conversation read/note and Conversation text read/write plus Activity body read/write, as the baseline already enforces; it does not require activity.create or current ownership. The correction to the earlier T01 wording preserves existing behavior.

## Creation and recovery refinement — scoped Ready

Each public POST obtains a fresh current Conversation note admission, including receipt replay. A separate stable effect command is derived from tenant/principal/legacy route/key, preserving permanent effect dedup beyond the public response TTL. Chat first checks imported completed public receipts, then resumes the existing effect command before preparing another one. Different bodies under the same key conflict. Chat stores only body/request digests and reference metadata; plaintext travels transiently to CRM and persists only in Activity.body.

The effect command pins Conversation authority, current session (nullable for a closed Conversation), note-body digest and original public request hash/key/correlation. Identity admits it under the same note rights. Chat atomically rechecks the full authority/session snapshot and inserts a pending crm-note dependency under registry/command locks. This acceptance point orders the note before later session/ownership changes; it holds no network transaction. CRM requires the prepared Chat proof, pending dependency and its current Identity admission. CRM atomically creates Activity, owner/team history, minimized audit, notification outbox and a terminal crm_owner_command receipt. Child key is parent-command:note:v1; the CRM receipt uses that parent's UUID as its tenant-local command key.

CRM create and abort serialize on that permanent receipt row. Abort installs a tombstone even before create arrives. Lost ACK is resolved by the same receipt; it never creates another Activity. If abort wins, delayed create cannot win. If create wins, recovery returns the immutable Activity reference and Chat must finish its reference, contribution and public receipt; it never deletes the Activity as compensation. A permanently aborted original effect cannot be retried as a new effect under the same key; the public error makes the terminal outcome explicit and a new action uses a new key.

Chat reconciliation uses the accepted session/owner snapshot even if the Conversation was subsequently closed or assigned. It inserts the Activity reference and note contribution once, without body, and completes the original legacy receipt with status201. Creation without an active session adds no session contribution. Pending/committed remote child state prevents generic parent abort. Identity command-abort dispatches note effects to the note-aware resolver: CRM abort/read first, then reconcile a committed child or mark an aborted child and abort the parent. Owner outage leaves the admission unsettled and the barrier incomplete. A fresh public delivery admission still fences a delayed response after logout.

The CRM notification remains durable for the T06 delivery consumer; immediate Chat reconciliation is idempotent with later notification delivery. Generic Activity update/archive binding and notifications must use Chat proof/own retained binding after extraction; the legacy foreign-registry join cannot remain mounted. T05/T06 acceptance must cover these before main activation. [Storage review](../data/chat-note-candidate.md) controls the scoped native fixture DDL; main migration/rollback is still T09-gated.

Required write acceptance: nonowner note without activity.create, Conversation/Activity field denial, legacy completed receipt, body-key conflict, duplicate/concurrent retry, lost ACK before/after CRM commit, crash before child/after child/after local reconcile, native logout races on both sides of acceptance, closed/reassigned session reconciliation, tenant/workload negatives, CRM outage retaining pending admission, durable one-note/one-contribution/outbox evidence. These remain NOT_RUN until recorded in the runbook.
