## Common boundary

All new operations are POST `/internal/v1/owners/{owner}/{operation}` with exact path/body operation, schema_version=1, UUID request_id/correlation_id/tenant_id. The generated catalog fixes caller allowlists, request/result definitions, admission mode and capability. Names describe target contracts, not currently deployed routes. Use existing TLS1.3 workload transport/registry, SAN service identity and per-request tenant authorization including keepalive; extend enrollment to the exact catalog callers. No headers/body may impersonate another service. No new token scheme, password, Human cookie or raw app token crosses domain services. BFF obtains an opaque Identity delegation reference using native session+CSRF, or app authentication+quota; services use their registered service actor. References never grant authority by possession.

2s RPC deadline by default, 256KiB raw body cap (existing dispatch/control/exchange keep their smaller caps), application bounds and strict JSON validation before persistence. CHG-20261025-05 defines a fixed10s outer composition deadline for Chat owner command envelopes whose generated request schema requires both actor and command_id: these prepare local state, obtain current authority, hydrate/reserve references and settle across network hops. This includes Human and admitted app reads/mutations. It does not mount any otherwise unavailable operation. Actorless Chat proof/abort/event receipts retain2s. Other-owner RPCs retain2s except the previously enumerated composed Routing reads and the exact nested Inbox composition operations below. Exact registry/dispatch deadlines and request-body caps remain unchanged. Client/server select the same profile; no business retry or cached authorization. History/queue/Conversation-list responses retain their existing8MiB cap. Timeout recovers the same durable command/receipt and never proves absence of a committed effect. Reject duplicate JSON keys, nonfinite numbers, unknown properties, invalid UUIDs, unsupported versions and path/body mismatch. Version/counter strings are unsigned decimal, compare with BigInt, fail on overflow above uint64. SHA256 is lowercase hex over canonical sorted-key JSON UTF-8, preserves array order, excludes request_id/correlation_id and includes tenant, actor, operation, route legacy key, payload and all expected versions. Dependency receipt IDs are excluded from this core digest to avoid a circular reservation binding: the prepared core is immutable, and each owner appends only a verified dependency receipt bound to that core digest. Required dependency slots are fixed by operation; no caller can remove/replace a slot, and apply rejects missing/unsettled prerequisites. They are durable local command metadata, not editable authorization claims. Limits are safety bounds, not permission to truncate silently; return LIMIT_EXCEEDED422. Do not log payloads.

Every reply echoes request_id; caller verifies TLS owner, tenant, command/event key, binding digest and expected state. Legacy public domain failures remain the existing sanitized public response at the BFF compatibility adapter; internal generic errors map to the existing equivalent status/code, while domain-specific errors use `{schema_version,request_id,code:DOMAIN_ERROR,public_error}` with the preserved strict AuthErrorResponse. Only that operation’s existing allowlisted domain error codes and sanitized messages/field names may be emitted; never copy a remote exception string. BFF unwraps it with the original HTTP status. Errors are sanitized `{schema_version,request_id,code}`: INVALID_REQUEST400, UNAUTHENTICATED401, FORBIDDEN/REVOKED403, NOT_FOUND404 for hidden/foreign resources, CONFLICT/STALE_VERSION/CAPACITY/INVALID_TRANSITION409, LIMIT_EXCEEDED/REFERENCE_INVALID422, PRECONDITION_REQUIRED428, DEPENDENCY_UNAVAILABLE503. Unknown after timeout is a local pending state, not an assertion of failure. Reads return no-store. Retry with the identical command key/digest; changed payload409. Retry transient transport/503 at 1,5,30,120,600s capped with jitter; never invent a new command ID. Business conflicts require a newly reviewed request. No automatic provider retry; D2 rules remain authoritative.

## Non-send admission and revocation

An `allowed=true` remote check is insufficient. Identity owns a durable per-command admission and a **drain barrier** under the same native account/session/tenant authorization serialization as policy changes. This preserves observable revoke completion ordering without keeping SQL locks across network calls. It trades availability during owner outage for safety. Identity cannot return completed logout/revoke/policy-change success while affected admitted operations can still produce new effects. A slow barrier keeps the existing request pending up to its HTTP deadline, then503; retry/status resolves the existing barrier. The session is immediately closing and rejects new requests even if logout response is lost. UI must not treat503 as a successful permission change. No grant TTL silently releases a barrier.

1. Owner prepares an immutable `CommandBinding` and durable command row, before business effects. It records principal/delegation, requested operation/fields, exact resource owner/team/share/version/control snapshot, target owner/team, all dependency receipt IDs, payload hash, legacy receipt identity, graph/action identity when present. `command-proof` returns it only to Identity and participating owners. Prepare may be superseded by later record changes; it reserves no permission. Existing Conversation counters must be positive; zero is allowed only for not-yet-created aggregate or absent owner/control counter in a catalog. Collection proofs use tenant_id as the aggregate resource ID and the explicit catalog object key, with per-row resource_contexts/candidate_digest in command-proof; this is never an all-record permission or a wildcard tenant. Identity rejects an aggregate/field/object combination not registered for the operation.
2. Identity `admit` first obtains the prepared proof from the authenticated owner outside SQL. In a short Identity transaction it locks native account/session/security revision then tenant policy, checks no closing barrier, active tenant/membership/principal, seat, own/team/all scope, field deny (existing tenant-super-admin exception), app parent/message scope intersection and quota, or exact service actor rights. It evaluates target membership/kind/team/chat seat/availability/read+reply+text eligibility for routing; team clearing still requires configure. Takeover target must equal authenticated Human. It persists admission keyed by tenant+owner+command, bound to proof digest and current auth revision, with explicitly allowed fields. An ID is not a bearer grant. No dispatch send grant can enter this protocol.
3. **Admission linearizes at the Identity commit.** Revoke before admission rejects it. Revoke after admission closes the gate, drains that exact operation, then completes. Chat reads the admission receipt from Identity outside SQL, validates bindings, then in a Chat-local transaction CASes the prepared row and all resource/owner/control/dependency fences; it applies once or records terminal aborted. State+receipt+audit+outbox commit atomically. Only this prepared command may use this admission; it cannot authorize another operation/field/resource or a later retry generation.
4. Identity `settle` fetches the owning terminal proof outside SQL; only committed/aborted with matching digest can release the admission. Pending/404/outage is not absence proof. A recovery worker can ask owner `command-abort`; that races apply under the same command lock and persists an abort tombstone even before a delayed prepare. If apply won, report committed; if abort won, every delayed prepare/apply fails. Identity never fabricates owner abort. Revoke completion waits all admissions tied to affected account/session/principal/tenant/team/field/app/target eligibility (conservative whole-tenant drain allowed). Global password reset closes account admission before enumerating its tenant admissions; no enumeration gap.
5. Crash before admit has no effect; crash/lost ACK after admit recovers same command from receipt and may apply or abort. Crash after business commit before settle only delays barrier completion, never repeats an effect. Replay of business output requires a **new read admission** under current rights; recovery peers may read minimized terminal proof without the revoked Human's permissions, never original bodies. Failed preparation and tombstones persist through restore horizon; local scope has no automatic purge. A transport lease expiry cannot revoke durable authority or prove no effect.

Read admission uses the same protocol: owner builds an immutable bounded page/result candidate in a short local snapshot transaction, stores digest and resource policy facts, ends SQL, admits exact selection/fields at Identity, then checks the current local resource versions before disclosing the page. Mismatch discards/retries preparation, never mixes scopes. Mark delivery completed before releasing admission; an already admitted network response can arrive late, as with a read ordered before revoke. No future page is authorized. Deadline/restart discards a not-yet-delivered candidate via abort; result lookup requires fresh read rights. Collection/batch read proof records each candidate row resource context (max100 per page) in owner storage, referenced by the page digest; Identity fetches these immutable contexts through the owning command proof before admission. For complete-source aggregate reads it checks explicit read-all and every projected/filter/metric field for every source object instead of inferring rights from a sample row. Large batches split into independently admitted pages; reporting cannot silently claim a global snapshot. Barrier-status is restricted to the original delegation’s barrier (even if that delegation is now closing) or an explicitly authorized operator; no arbitrary BFF barrier enumeration. No transcript/policy copy is included in Identity proof: field paths, resource refs and digests only.

## Inbox read latency refinement — CHG-20261027-05

FIX-20261027-01: the existing 10s Chat read composition budget must include nested owner composition. Identity `admit`, `settle`, `admission-cursor-subject`, `admission-workspace-policy`, `admission-conversation-policy`, `admission-contact-policy`, `admission-contact-batch-policy`, and `admission-note-policy` use a fixed 5s budget; CRM `contact-summary-read`, `contact-summary-batch`, and `note-list` use 5s. These operations themselves fetch owner proof/current policy over HTTP and were incorrectly treated as elementary 2s reads. Other operations and registry/dispatch freshness remain unchanged. An older caller's shorter timeout remains fail-closed and retry-compatible; no schema or database migration.

Protocol clients reuse bounded idle HTTP/TLS connections, with fresh peer authentication and current tenant/service authorization on every request, including reused sockets. Independent caller/receiver checks can execute concurrently, but both must pass before request dispatch or handler invocation. No authority decision is cached across requests. History rich-content and reply hydration is batched within the same Chat transaction and tenant/conversation scope; pagination and field redaction are unchanged.

Docker/WSL wall-clock steps were measured during this defect. Registry freshness retains the signed timestamp, nonce/tenant/peer checks and skew bounds; elapsed time uses a monotonic clock. Only when an otherwise verified signed reply fails timestamp bounds AND the local wall/monotonic delta proves a clock step exceeding250ms may the registry reader discard it and request one fresh nonce. Both attempts share the original2s monotonic budget; the second reply must pass every ordinary freshness check. Stale signed replies on a stable clock, invalid signatures/nonce/tenant/peer, outages and business commands are never retried by this rule. This is a read-only registry bootstrap recovery, not a relaxation of authorization or certificate/session expiry.

## Assignment, takeover, close and Routing saga

Scoped collection-read refinement (CHG-20261022-02): the [workspace queue](chat-queue-candidate.md) admits a registered tenant query aggregate and digest-bound filter paths, then obtains finite current Identity predicates for every matching row and count. It does not infer read-all from sampled candidates. Selected Conversation resource contexts are supplied by authenticated Chat to the current admission policy endpoint in bounded batches; CRM independently supplies its own Contact authority contexts. Chat rechecks the complete local query snapshot before terminal delivery. The parent admission remains open throughout and is abortable by Identity barriers. This replaces persisted per-row candidate contexts for these explicitly listed read-only query operations; it does not authorize a general collection command, shared SQL or raw Access transport. Transcript/Contact bodies are never persisted in the query proof.

Binding includes conversation_id/session_id, expected record_version/owner_revision/control_revision, target owner kind/principal/team, reason and stable command ID. Chat prepares; Routing `capacity-reserve` checks pinned queue configuration/skills, enabled profile and workload under its own tenant/capacity locks, counts pending reservations + confirmed allocations, and returns a durable reservation tied to that exact binding. Target eligibility is part of Identity admission, not the Routing cache. Reserve for the same current allocation is a no-extra-slot transfer; same-owner assignment still advances owner/control revision once. Managed work cannot target an unmanaged Human or bypass cap; unmanaged compatibility is explicit `not-managed` reservation, based on authoritative Routing enrollment, never a caller flag.

After all remote preparation and Identity admission, the one Chat transaction revalidates active episode/version/owner/team/shares, local ACL facts, dependency IDs and reservation binding; writes registry/history/contribution/activity, wakes snooze, increments owner/control/registry counters, cancels queued and remote_queued intents and messages, and writes terminal receipt/audit/control+legacy events. Already sending/unknown remains in flight and reconcilable. No remote calls occur inside that transaction. Close also ends the episode and emits completed-work evidence; pending/snoozed never releases load. Target capacity is held conservatively until reconciliation.

Chat response confirms local ownership only. Outbox drives Routing `capacity-confirm` after Routing reads terminal Chat proof; it converts reservation to allocation and releases previous allocation atomically in Routing. `capacity-release` accepts only a Chat abort proof or a newer closed/transferred owner proof, never timeout/404. `capacity-status` recovers lost reserve/confirm/release ACK. Queue/profile/skills disabling or capacity reduction closes a Routing admission barrier, blocks new reservations, and drains previously reserved commands before returning completed configuration change; historical allocations may remain above a reduced cap as today. A reservation has no auto-expiry: sweeper at30s requests Chat abort/status; unavailable holds capacity and reports blocked. Reordered confirmations compare owner_revision and immutable session/allocation identity; old confirm cannot overwrite newer owner, old release cannot release newer allocation. Routing completed work is monotonic. For unassign, reserve returns no new slot and confirmation releases only the old revision. For close, release follows the committed close proof. Reconciliation never rolls Chat back to an older owner.

AI/Chatflow receive existing `chat.registry.changed.v1` cumulative watermarks through the durable transport below. Cancel precedes pause; fence local tool/node leases and release their own capacity once. Chat fences future effects immediately at local commit regardless of remote ACK. New-generation work survives old events; resume requires explicit current generation admission and pinned graph. Existing D2 claim/consume/result semantics remain unchanged. Assignment/status displays remote reconciliation pending if needed; never falsely says in-flight provider delivery was cancelled.

Legacy graph versions and receipt paths are not rewritten; adapters perform field aliases at read time only.


Reporting owns its source adapters and derived snapshots/facts. Chat stores conversation/session attribution and lifecycle with tenant/version semantics and exposes its authorized domain API/events. No dedicated snapshot-prepare/validate/page/release or report facts pipeline is required for Chat acceptance. Cross-service SQL and stale retained registry fallback are prohibited; unavailable consumer integration remains explicit and is accepted by its owner.

## Durable event delivery without a broker prerequisite

ADR-025 chooses owner HTTPS push from each local transactional outbox to `event-deliver`, plus `event-status` and producer `event-read` for immutable source verification. MySQL is durable; Redis may wake workers but never ACK an effect. This supersedes the proposed JetStream profile for this D3 transport only. ADR-022 Kafka object-change design remains pending; this bridge carries existing M2 Workflow events without implementing that separate object-change stream.

Outbox transaction records event ID/version, producer, tenant, aggregate/sequence, correlation, digest and fixed subscription revision; per-consumer delivery state is separate. Transport sequence is per producer+tenant+aggregate+consumer subscription, so filtering another event type cannot create an artificial gap. Sequence/consumer are transport metadata outside the immutable original event digest; importing legacy events assigns a contiguous delivery sequence without rewriting original payload/ID/version. Relay leases locally (30s, fenced token), ends SQL, pushes event, then marks delivery acknowledged only for a validated terminal consumer receipt. No mutation of producer event body/ID on retry. Consumer validates peer+producer+tenant subscription, strict event shape, envelope/data binding and source digest (owner fetch outside SQL if notice-only), then in one local transaction commits inbox dedup + effect + audit/child outbox. Only afterward return applied/duplicate/reconciled ACK. Inbox durable key `(tenant_id,producer,event_id,consumer)`; same key/different digest quarantines. It never references remote outbox by SQL FK.

Lost ACK repeats same event or queries status. Timeout/received/pending is not applied; unknown404 is retried, not dropped. Reordered cumulative control snapshots reconcile maxima; ordered business streams keep a per-producer/aggregate subscription sequence (not record_version) and buffer gaps. Producer `event-replay` supplies missing events after cursor, max100, with high watermark; gap cannot be skipped. Snapshot-based consumers may reconcile only when their handler explicitly supports it; Workflow trigger history must replay exact events. Existing events retain their schema_version and original event ID; new envelope carries transport version separately. No ordering across producers is claimed.

Retry schedule as above; after10 unsuccessful deliveries quarantine with alert but retain payload/reference and per-consumer position. Operators can retry the same key after fixing the cause, never assign another event ID. No automatic purge in local D3; retention must cover all consumer watermarks, unresolved operations and backup/restore before a future policy enables purge. Restored inbox/outbox replays are safe. Removing a subscription requires drain+tombstone; backlog cannot be marked sent merely because a process was removed. Worker scans paginated tenant allowlist every1s; bounded100 deliveries/tick, concurrency4, no overlapping ticks;30s orphan reconciliation. No background process is installed by T01.

Eight existing Chat consumers retain names and exact event bodies; catalog below binds producer and handler behavior. Outside Chat, existing Human Routing four consumers, Workflow four consumers, Identity/routing/runtime access consumers and new registry projections receive owner delivery. Cleanup after revoke uses narrow authenticated system purpose, never revoked actor impersonation; any new business effect must obtain current admission. [Consumer mapping](../architecture/chat-owner-consumers.md) defines every subscription and ordering mode.
