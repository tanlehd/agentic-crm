# Human conversation routing — PLAN-045 / SRC-084

2026-10-17 · **Ready for this bounded monolith implementation.** User approved implementation of [logical design](../data/conversation-routing-erd.md) with administrator/team configuration, automatic next assignment, agent reply/close, supervision/reassignment and performance evidence. CHG-20261017-05. Broader distributed routing/visual policy builder remains a separate extension.

## Scope and decisions

Routing owns skill catalog, team skill grants, Human capacity profile, versioned queues, work/entry/attempt/allocation. Identity owns memberships/availability/auth; Chat owns sessions, owner/history and replies. Baseline application ports share an existing monolith UoW under exclusive tenant authorization lock. No cross-service SQL/FK; no extraction. Owner + capacity commit atomically, so no externally visible reservation/unknown outcome is needed in this slice. Remote saga required before service extraction; never simulate it with TTL release.

Admin explicitly creates profiles (capacity0…100) and enables queue(s). No automatic grant/default queue on migration; existing behavior remains for non-enrolled tenants. Skills granted to a team qualify its current members; eligibility still requires current Human/chat seat, availability, read/reply/field permissions. Required queue skills must be present in the target team grants. Missing skills block routing; no bypass through manual transfer. One queue targets one team, optional connection, and required skills. Lowest priority number then queue ID chooses source match; pinned immutable version governs an existing entry. Algorithm least-loaded, principal ID tie-break. Entry priority then oldest wait/ID governs dispatch. No custom AST/overflow/offer/weighted-capacity UI in this slice.

First authorized queue publication provisions a dedicated Identity-owned `human_routing_dispatch` role/service actor through Identity port, with only conversation.read/assign all. It is checked live on every dispatch; disabling actor or revoking grants blocks new assignment with `routing_actor_unavailable` while reconciliation still releases completed workload. Existing revoked actors are never recreated/re-enabled by publication. Profiles require chat capability. Enrollment timestamps use Chat session opening / latest owner history, not a fabricated historical start. Report reply facts are restricted to managed session IDs (max5000 in30day report window), not all tenant conversations. Agent-facing output honors owner/team field denies.

Managed Human profiles count all active owned sessions across queues, including pending/snoozed. Backfill on profile enable preserves current owners and records existing load even above new cap; no new assignment until below cap. All normal/manual/takeover/Workflow Human assignments check capacity through the same Routing path. Unmanaged Human target is rejected for an enrolled work to prevent bypass; existing unmanaged conversations retain compatibility. One work per session; close ends it; another inbound session creates new work. No slot release on tab close. Session closure and owner changes reconcile from live Chat state; stale/duplicate events cannot resurrect completed work. Queue reassignment opens a new wait cycle; failed operation rolls back owner, allocation and queue changes together.

Native engine wakes from durable session opened/closed, ownership and principal-access events. Worker delivers events on its existing1s tick; bounded30s recovery scans enabled/profile tenants. Configuration/manual reroute dispatch in their command transaction. UI refresh5s is independent of engine. No hard production latency claim. R1 bound:500 active/managed sessions per tenant snapshot,100 waiting dispatches per invocation,50 queues/200 skills/500 profiles. Exceeding limits fails visibly; does not silently truncate reports. Configured tenant sweep is paginated.

## API / permission / compatibility

Native session+tenant required, mutations require CSRF/origin, JSON, printable Idempotency-Key1…128, strict fields, If-Match quoted numeric for updates (0=create singleton),200 mutation envelope `{data,meta}`. Errors400 invalid,403 forbidden,404 hidden/not found,409 version/capacity/ineligible,422 reference/limit,428 missing version,503 transient. Replay checks live permissions before returning; payload mismatch409. Existing endpoints unchanged.

`GET /api/v1/human-routing`: admin snapshot config, current workload/queue, historical performance (last30days; completed allocations within window, open counts all current). Requires `routing.read:all` + configure and conversation read/assign all, no field-denied owner/team. Directory via Identity port only. `GET /api/v1/human-routing/mine`: chat seat and conversation.read; only caller profile and currently assigned work that caller can read. Includes allocation IDs/timestamps for new-assignment alert and existing Inbox navigation; no global directory/report.

`POST /api/v1/human-routing/skills` `{key,name}` create, key lowercase dots/underscore/dash max64, name1…120. `POST .../team-skills` `{team_id,skill_ids}` replace bounded unique array, If-Match latest team grant version (0 empty). `POST .../profiles` `{principal_id,capacity,enabled}` version0/create or profile version/update. `POST .../queues` `{id?,name,team_id,connection_id,skill_ids,priority,enabled}` create version0/update head version; new immutable version on every update. `POST .../reroute` `{work_id,queue_id,owner_principal_id}` (owner nullable = auto queue) If-Match work version; requires existing conversation.assign on live record. Config/reroute require `routing.manage:all` + configure + conversation read/assign all. Super-admin gains matrix rights intrinsically; no role row rewrites. Team skill updates validate active chat/general team; profiles active Human references; channels via authorized Channel port. Availability remains Identity setting.

Reroute to a specified agent checks target queue skills/team/availability/permission/capacity. No administrator cap override. Failure leaves original owner untouched. Owner null releases current allocation and enters queue; auto dispatcher may immediately assign same eligible agent. Pausing queue stops new admission and dispatch for its waiting entries; active work continues and may close; resuming wakes backlog. Existing entry config stays pinned across publication; explicit reroute applies latest queue version.

## Filled table template — common fields and rules

All9 new tables below: business scope; Routing writer; target crm_routing, physical agentic_crm until extraction; forward35 only. `T`=`tenant_id CHAR(36) ASCII ascii_bin NOT NULL`, `ID` same CHAR36, `V` BIGINT UNSIGNED NOT NULL DEFAULT1 CHECK>=1, `D` UTC DATETIME(6), `S(n)` VARCHAR(n) utf8mb4_0900_as_cs. No tenant default; entity PK(T,id), links described below. Every unspecified column is NOT NULL; `?` explicitly nullable. ID references external Identity/Chat/Channels are logical only, validated through ports; same-Routing FKs include tenant. Common created_at D default CURRENT_TIMESTAMP(6); mutable updated_at same default; no automatic TTL deletion.

## Performance semantics / UI

Admin screen tabs Configuration / Workload & queue / Performance. Agent Inbox shows current load and confirmed new-assignment alert with open-conversation action. Admin can reroute waiting or active work from workload table. Report: assignments in last30days; completions credited only to allocation active at session close; transfers separate, never count as completion; average handling duration for completed allocations (wall-clock assigned→closed, includes pending/snooze; not active typing time); queue wait average on successfully assigned entries; submitted Human replies counted from canonical session_contribution by actor in same time window, labeled submitted, not delivered. Historical team at allocation time, never current membership attribution. Period timezone UTC, display local; no fake zero when unavailable. This is connected operational performance report; generic cross-service Report Builder remains separate.
