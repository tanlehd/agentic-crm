# Native Human Routing dispatch

SRC-109/T06, CHG-20261023-15, Codex2026-10-23, Ready. Extends [source reconciliation](chat-routing-reconciliation.md) with automatic Human dispatch; no AI execution, new queue business rules or main worker activation.

Add Routing-only `chat/routing-proposal`: fresh service admission for a real Conversation and selected queue team. Only registered `human_routing_dispatch` with current Conversation read-all/assign-all may invoke it. Reuse the bounded Identity Human candidate policy from assignment-directory; native service access does not widen either public Human directory endpoint. Chat returns the current resource plus eligible targets after final local CAS and current directory comparison. No message/Contact body or raw Access is returned. The proposal is advisory; assignment reauthorizes and reserves independently.

Routing processes waiting entries in existing priority/wait/id order, checks pinned queue team skills and current enabled Human profiles, and ranks eligible Humans by allocated+reserved session load then principal ID. Pending/snoozed work remains allocated. No candidate means the existing blocked_reason vocabulary; no new Chat session is opened. Queue/profile/skill changes remain serialized through the Routing capacity gate.

Before any assignment HTTP, Routing durably stores one immutable prepared dispatch command for the work item in its existing routing_owner_command. Under the same gate, concurrent workers reuse that command. Its saved request includes the actual Chat resource/session, selected Human/team and exact work/entry/queue-version IDs. A pure protocol binding function yields the exact Chat child reference before sending; both owners use it. This makes an abort tombstone possible even if an earlier request/ACK is lost before prepare. It is data serialization, not a shared domain implementation or UoW.

New Routing-only `chat/routing-dispatch` validates the exact service command and prepares the pinned binding, then uses the existing ChatOwnership saga. Automatic history/contribution reason remains `human_routing`. Identity checks the current service and target Human; Routing reserve requires the same waiting work/entry/queue version, live profile, skill and capacity. Final Chat assignment still compares the entire current resource and active session, cancels only queued work and emits the same ownership effects. Caller snapshots are constraints, not authority. The optional binding pin is additive; old assignments without it keep their existing protocol.

The reply contains only exact command/state and reconciliation status. Lost ACK retries the saved request, never a new target/key. Permanent denial attempts authenticated abort with the precomputed reference; a committed winner is reconciled, never reversed. Aborted proof releases only that command's reservation. Network/owner outage or unresolved proof leaves the prepared job pending. A closed Routing gate may reconcile existing jobs but cannot choose a new assignment. The30s capacity sweeper resolves any late reservation from its current Chat proof; timeout/absence never releases unknown capacity. No main schedule is added by this candidate.

Routing marks its local dispatch terminal only after matching terminal proof and completed reconciliation. It preserves immutable requests/results for replay and does not fabricate Chat receipts. Source reconciliation repairs work/allocation projections after terminal outcomes. Required evidence: full actual Chat ownership effects through owner HTTP, least-load selection, unavailable/role/field/skill/capacity negatives, current actor revoke, queue config race, concurrent workers, lost before/after commit ACK, abort-before-prepare, no second assignment after retry and pending capacity recovery. No DDL; existing routing_owner_command rows are partitioned by operation. Public work/facts and reroute wiring remain separate T06 scope.
