# Chat command recovery — T06

CHG-20261023-21, Codex 2026-10-23, C2 Ready. Continues SRC-109/T06 after [event delivery](chat-event-delivery.md). Implements [terminal proof rules](chat-owner-v1.md) without replaying Human business requests or borrowing another actor's authorization. No API shape or DDL change.

The worker discovers at most100 commands older than30seconds per tick, within configured business tenants. It records a local `recovery` slot in the existing Chat dependency ledger, with remote_owner=`chat`, remote_command_id equal to the original command, child_key=`recovery:<command>`, receipt_id=NULL and immutable command-ref request_json. This is scheduling state, never an authorization receipt or an unresolved remote child. The slot is `prepared` until recovery completes, then `released`; it never uses `pending`/`committed` and cannot falsely block parent abort or appear in public proof dependencies. Existing business slots and proof JSON remain unchanged.

The slot uses the existing next_attempt_at, lease_token, lease_until and version columns. Claim uses a30second fenced lease; network calls run outside SQL. Failure schedules another bounded retry with no deletion or guessed terminal result. Completion is a conditional update of the original lease; an expired worker cannot release or reschedule a newer claim. Recovery RPCs use the original command/receipt identity and existing idempotent terminal handlers; lease expiry is not proof that a remote child had no effect.

Every operation has an explicitly registered recovery handler. Missing handlers retain pending recovery and report unsupported; there is no generic business-request replay. Notes and need-outcome first resolve their original CRM/Sales child; ingress resolves referral and releases its existing holds; ownership reconciles terminal Routing/Identity receipts. Other local-only commands can race an abort against commit, then settle existing admission/reference receipts. Prepared commands never resume under a replacement Human session. Unsupported operation names must be reported in the T06 inventory before runtime acceptance.

The concrete handler registry is `services/chat/src/command-reconciliation.ts`. It validates terminal receipt IDs/digests before completing known dependency reconciliation. An admission or capacity reservation whose ACK was never persisted is still recoverable by its owning service from the original Chat terminal proof; Chat does not fabricate that receipt or claim the remote row absent. Existing Identity/Routing drain contracts retain this responsibility. Snooze and outbound discovery also require an explicit tenant list; mutations continue through their existing revision/lease and writer-epoch checks.

Storage template refinement for [chat_owner_dependency](../data/chat-extraction-tables.md#crm_chatchat_owner_dependency): same business tenant/Chat writer, same PK/index/constraints/grants and bounded discovery; the local recovery slot stores only the minimized command ref, no new PII. Permanent original command/dedup remains retained. Old binaries ignore this slot (no receipt_id; prepared/released only); runtime cannot activate until the complete handler map is checked. No historical migration is changed and no startup DDL is added. Native tests must cover own grants, tenant isolation, lost completion/restart, lease expiry/stale worker, failed handler retention and unsupported operation handling.
