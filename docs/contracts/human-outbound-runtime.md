## Ready transport/composition scope

Move the Node-only TLS/strict JSON adapter to `packages/workload-transport`, consumed by backend and Connector. Keep backend re-exports for existing callers. No domain/SQL/framework code in this shared package. Review the explicit infrastructure import exception in the service lint rule; never allow arbitrary backend/domain imports. Build the package before its two consumers and include it in their Docker dependencies.

Remote current admission uses a **separate operator-pinned Ed25519 authority key**, not the TLS leaf key. Only Identity owns the signing private key; callers receive its verification public key and exact key ID through private operator config. Key replacement requires explicit deployment configuration; no key is learned from an untrusted response. This is the local deployment trust root, not an online CA/key-management service.

POST `/internal/v1/workloads/admit` accepts exactly `{schema_version:1,request_id,tenant_id,subject:{service,fingerprint}}`. Allowed client workloads chat/connector/identity; TLS1.3 CA/URI/leaf checks unchanged. Identity checks its own TLS leaf and actual peer against current native registry for the business tenant, then checks the requested subject. Request body cannot substitute caller identity. Response contains exact `schema_version,key_id,request_id,tenant_id,caller,issuer,subject,issued_at_ms,decision:'allow',signature`; caller/issuer are actual TLS identities, subject matches request. Ed25519 signs the canonical JSON of all fields except signature.

The narrow bootstrap client only sends this admission DTO to this exact path. It validates the CA and Identity URI, verifies pinned authority signature, nonce/request correlation, tenant, caller and issuer TLS fingerprints, subject, schema and request-time freshness (maximum2s). Unknown/extra fields, deny/error, changed nonce/subject, wrong key or stale reply fail closed. No portable/cacheable allow: every business request rechecks own and peer current admission. The bootstrap endpoint authenticates through native SQL directly and never calls itself. No generic no-op CurrentAuthority or TLS verification bypass is exposed. Authority outage stops business admission; never falls back to static CA allow. CHG-20261027-05 uses monotonic elapsed time for that same2s budget. Only a measured local clock step that invalidates an otherwise verified timestamp permits one fresh-nonce registry read within the original deadline; the suspect proof is discarded and all freshness checks apply again. Stable-clock stale replies and business commands are never retried. See [Inbox read refinement](chat-owner-v1.md#inbox-read-latency-refinement--chg-20261027-05).

Identity routes issue/consume/read use `IdentityDispatchLedger`; Chat claim/proof/result use `NativeChatClaims/Results`; Connector payload/prepare/begin/read use existing stores and `AttemptExecutor`. Each route validates strict existing operation schemas, binds actual TLS caller, enforces owning caller allowlist and tenant, and propagates current-registry errors. Connector never reads Identity SQL. Owning adapters must validate response schema/correlation before consuming authority facts. No caller may supply provider callbacks or session verifier through private RPC bodies.

Additive read-only `/internal/v1/dispatch/intent-read` at Chat accepts existing strict ReceiptRead with receipt_id=intent_id, caller Connector only. It returns exactly schema_version1/request_id/receipt_id/state=`queued`/binding/resource_context. Chat rechecks active tenant, open/unarchived current owner+version, contact/connection, queued intent/message and payload digest under its baseline local transaction. Connector verifies exact binding and context against the current issued Identity grant before payload-put or prepare; a cancelled/stale queued intent denies. This checks current Chat authority without inventing a cancellation ID. Staging cannot send; later Chat claim CAS still arbitrates a concurrent cancellation. Existing full cancellation propagation remains a separately gated consumer, not silently enabled here.

## Ready durable command and coordinator scope — CHG-20261018-25

Public `POST messages/messages-v2` keeps its existing body, ACL, CSRF, idempotency and202/status URL. Explicit local `HUMAN_OUTBOUND_MODE=connector` enables only mock_messenger Human text; unsupported connections fail before creating an intent, never fall back to another sender. Default remains legacy. Authenticated controller enrolls a native Identity delegation through a baseline local Identity application port **before** the Chat command transaction. That port locks active tenant→native account/session→principal, stores only the existing Identity verifier/revision record, and returns an opaque delegation ID/principal ID. No session verifier enters Chat SQL, worker config, RPC or logs. A denied/replayed Chat command can leave an inert Identity delegation; it cannot send without a matching Chat job and current grant. No network or separate Identity transaction is opened while Chat holds locks. Worker grant issuance and consumption recheck native session/current rights against the exact Chat resource snapshot.

Chat transaction atomically creates intent, message, durable job, workspace/acquisition updates, audit and public idempotency receipt. The [table design](../data/chat-outbound-job.md) specifies forward42. Durable internal intent states `remote_queued`, `remote_sending`, `remote_unknown` fence old sender binaries: their queued/sending/unknown scans, direct dispatch, expiry, reconcile and retry predicates never match these rows. Public intent responses normalize these states; message keeps existing public queued/sending/unknown states. Terminal sent/cancelled retains normal names. Remote route never reverts to legacy on config disable or rollback. New cancellation helper includes remote_queued; old takeover/close still changes owner/version, so live Chat claim denies even if its old cancellation helper does not recognize remote_queued. Supported rollback disables new enrollment but retains compatible status presentation/recovery; pre42 binaries are not a supported UI rollback, although their sender cannot take these intents.

Worker uses durable phases issue→payload→prepare→claim→begin→deliver, a30s lease token/CAS and bounded batches. Each RPC has a stable per-job operation request ID; no SQL transaction spans a network call. Save each phase only under the current lease. If ACK or phase-save is lost, repeat the same operation; never allocate a new attempt/delegation/grant as a retry. Identity grant remains10s with no extension. Failed dependency retries back off (capped30s); after25failed rounds mark job attention, preserving phase/IDs for investigation. Owner or session changes prevent fresh send; this is not an auto-renewal workflow.

Add two compatible private Connector routes, caller Chat only, reusing strict existing DTOs:

- `/internal/v1/dispatch/connector-claim`: ChatClaim body; validate durable prepared payload/grant binding locally, then Connector calls Chat claim over its own TLS identity. Return exact correlated claimed receipt. Replays may read an immutable claim after takeover; cannot create a fresh claim without live Identity authority at Chat.
- `/internal/v1/dispatch/connector-deliver`: ReceiptRead, receipt_id=attempt_id. Recover only this matching expired admitting/started attempt to unknown, read the durable result, then Connector calls Chat connector-result. Stable result request ID is derived from tenant+attempt+outcome, with distinct unknown/sent IDs. Return correlated sent/unknown receipt after Chat ACK. Nonterminal prepared/admitting/started returns its receipt for bounded retry. No Identity Human session is required to reconcile an already persisted result; current workload/tenant admission and Chat receipt verification still apply. This route never calls a sender.

Connector begin remains the sole path into AttemptExecutor. Coordinator sets phase begin before requesting it; after an uncertain response it queries the existing attempt first. prepared may retry the identical begin; admitting/started/sent/unknown must move to deliver without another begin. Expired admitting/started becomes unknown, never retryable failed. Result delivery after process restart/logout/takeover uses persisted receipts and can only advance unknown→sent with matching proof. A lease loss cannot produce a second send because Connector's durable guard and one-use continuation own that decision. No caller spoofs Connector to claim or deliver.
