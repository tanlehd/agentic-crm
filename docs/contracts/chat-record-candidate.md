CRM calls Chat `record-get` and `record-patch` for the existing generic envelope. Chat reads only its own registry and Conversation. Standard fields are `contact_id`, `status`, `opened_at`, `closed_at`; no Contact body or transcript is hydrated. Each field, including custom values, is filtered by current Identity read policy. Envelope ownership/version fields retain the generic CRM contract. Reads use a fresh admission and recheck the complete local snapshot before delivery.

PATCH accepts only nonempty custom values and empty/absent standard fields, with expected record version and public idempotency key. Owner/lifecycle changes continue through their dedicated commands. A stable command UUID binds tenant, Human principal, generic route and key. The first request resolves CRM metadata; retries recover the original schema/delegation from the durable command, even after metadata publication. Changed public body/version conflicts. No new table or migration.

The existing private `custom-values-patch` gains optional `hydrate_record: true`; absence preserves the T04 immutable empty-fields response. New hydrated commands bind optional `record_read_fields` to all proposed output keys (at most200). Identity requires current read/update and write+read for patched fields, then returns the readable subset of output fields. Chat filters and stores that exact response atomically with the mutation. Response delivery, including the first attempt, separately requires current read permission for every stored standard/custom field. Revoked fields deny the entire stored response; replay never silently removes them, rereads current values, or reapplies the write. The optional binding participates in the digest; old absent bindings remain unchanged.

The native public candidate adapter validates session/Origin/CSRF, tenant, body bounds, If-Match and idempotency headers, then invokes the CRM-authenticated owner hop.
