# Independent Chat runtime composition

CHG-20261025-02, SRC-109/T07 DONE, Codex 2026-10-25. [Runtime acceptance](../quality/t07-chat-runtime-acceptance.md) after [T06 acceptance](../quality/t06-chat-boundary-acceptance.md). No new business endpoint, table or consumer feature.

One Chat package/image provides API and worker modes. API mounts the reviewed owner routes, ingress exchange, dispatch claim/result and recovery routes on one authenticated workload listener. Duplicate routes fail startup. All tenant-bearing routes reject tenants outside the explicit configured tenant list. No baseline domain imports or other-owner SQL. Workers use the same retained Chat schema and epoch, with their own credentials.

Configuration is explicit: own DB host/port/name/user/password, writer epoch, tenant list, workload material/registry, owner URLs, separate dispatch Identity/Connector URLs, listening ports and retained cursor keys. Missing/invalid configuration fails startup. Reuse existing history/catalog/workspace/activity/external keys; no generated startup key or rotation. URLs obey the selected workload protocol, no embedded credentials/query/path. Optional Sales/Workflow/event receivers are configured when available; missing consumers keep durable backlog and fail dependent operations explicitly. Their rollout is not a Chat readiness gate.

Startup verifies packaged migration checksums and the actual journal, restricted owning-schema grants and every configured active writer epoch. API dependency readiness checks native Identity/CRM/Connector/Routing authenticated readiness endpoints; it never reports ready from process liveness alone. Liveness is a separate local health listener. Worker readiness reports own DB/writer gates and completed scheduler rounds. Metrics expose bounded aggregate counts only, no tokens, transcript or record identifiers.

CHAT_WORKER_JOBS defaults to all six jobs; explicit subsets support staged single-writer activation and isolated retained tests. Metrics expose the configured jobs; a subset does not certify full worker parity. Worker rounds call existing durable outbound, command recovery, snooze, event relay and Activity recovery implementations. Ingress discovery scans only received rows of explicit tenants in bounded UUID order and invokes the existing current-authority `process` path. Its scan cursor is ephemeral; inbox/commands/receipts remain MySQL authority, so restart resumes retained rows. It does not rerun processed/failed messages. One scanner failure does not prevent independent local consumers from advancing. Graceful shutdown stops new rounds/requests and waits for bounded in-flight work before closing the own pool; persisted leases/receipts handle an interrupted process.

Runtime scheduler batches ingress one row per tenant and outbound/recovery/event/activity one item per job per round; snooze retains its bounded local SQL scan. This keeps a large retained backlog from monopolizing a round or delaying shutdown behind many remote requests. Stop prevents the next job/item; interrupted leases remain durable. Standalone scanner default budgets remain compatible.

Migration remains a separate operator command using existing immutable Chat migrations and privileged operator credentials; API/worker never migrate or provision grants. Candidate Compose starts only Chat API/worker against retained synthetic config. It does not start/rebuild owners or route main traffic. T07 requires build/package/no-domain-import checks, actual process/image readiness, ingress/send smoke and restart; T08 verifies composed parity and T09 owns main cutover/fences.
