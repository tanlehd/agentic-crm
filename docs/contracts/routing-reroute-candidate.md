# Native Human reroute saga

SRC-109/T06, CHG-20261023-18, Codex2026-10-23, Ready. Preserves POST `/api/v1/human-routing/reroute` from [Human Routing](human-routing.md). No DDL or main mounting. Extends the existing ChatOwnership and Routing capacity protocol, not a second assignment implementation.

The public DTO stays work_id, queue_id and nullable owner_principal_id; native session/Origin/CSRF, Idempotency-Key and If-Match work version remain required. Routing preflights current configuration authority (routing.manage-all, configure capability, Conversation read/assign-all and owner/team read fields), including receipt replay. A fresh work reconciliation precedes new-command validation. Existing prepared commands resume their original request/delegation, never a newly selected queue, resource or target.

Routing validates the work version, active work/session and latest enabled queue, then requests an admitted Chat `routing-reroute-source` snapshot. Identity requires the same administrative rights; Chat supplies only the live resource/session after its own CAS. No candidate enumeration is needed. Routing checks that no unresolved capacity reservation already holds that session; unknown work cannot be treated as free or overwritten.

Before sending the effect, Routing stores one immutable `operation=reroute` job in routing_owner_command, keyed deterministically by tenant, Human, public route and idempotency key. It saves the public body/version hash and original response correlation, exact Chat request/binding and target queue version. Concurrent requests with the same key reuse this job; conflicting body/version fails. A pure codec computes the exact child reference before HTTP, allowing abort-before-prepare after a lost ACK.

New Routing-only `chat/routing-reroute` prepares the exact `routing-assignment` child with optional `routing_reroute={work_id,work_version,queue_version_id}`. Reason remains `human_routing`, actor remains Human. Identity checks current routing.manage/read-all/assign-all in addition to the existing assignment/field/target eligibility checks. Routing capacity verifies exact work/session/version and latest enabled queue/team, target profile/capacity/skills, and stores its existing reservation. It does not enqueue or release existing work before Chat wins its owner/session CAS. Failed or aborted transfer therefore leaves the previous owner, allocation and queue unchanged.

Committed Chat proof is the only trigger for Routing to cancel the old waiting entry and create the selected queue visit. A selected Human creates an assigned visit; null owner creates a waiting visit. Preserve same-owner capacity exception and existing historical allocations; do not rewrite old team facts. Queue/profile publication retains the existing capacity gate/drain ordering. Later owner/close proofs remain monotonic: an old confirmation must not revive or move newer work.

The Routing public receipt is saved atomically with its capacity confirmation, even when a newer terminal head already supersedes the assignment. It contains the actual current work version observed under the Routing gate, never a predicted version. New explicit assigned reroutes preserve the enqueue+assignment version increments; unassigned reroutes preserve the enqueue increment. Subsequent automatic dispatch may advance work again and is represented by its separate command. Lost confirmation/reply ACK retries terminal proof and returns the exact saved receipt. Unknown proof keeps the job pending; an abort cannot turn a committed Chat effect into a failed transfer.

Routing jobs have no separate reusable authorization grant: the mutating child carries the current Identity admission. Configuration/view recovery must reject reroute jobs. A worker may reconcile a saved job, but cannot replace its original delegation after logout. Public replay always rechecks current native administrative authority. Failed permanent children retain terminal denial and release only their matching reservation; late reservations still use the capacity sweeper.

Legacy unexpired public reroute receipts are imported into the existing routing_owner_command legacy_route/legacy_key/legacy_request_hash/result_json columns at T09, under a distinct committed legacy operation. The candidate reads these scoped receipts with the original body/version hash and response; no cross-service receipt SQL or fabricated owner proof. Fixture acceptance seeds an exact legacy receipt. T09 must add the fenced import and exact writer inventory before cutover. New native receipts are permanent per owner v1.

Required acceptance: actual full native assignment effects, selected/null/same-owner reroute, current queue/profile/skill/field/target rights, current work/resource/session races, old queue preservation on denial, concurrent same-key and competing assignment, late/newer confirmation, lost before/after commit and confirmation ACK, abort-before-prepare, replay/logout and imported legacy receipt/conflict. Keep public error mappings and headers. Main remains baseline until T09.
